# 110. Balanced Binary Tree

- **LeetCode 链接**: [Balanced Binary Tree](https://leetcode.com/problems/balanced-binary-tree/)
- **难度**: Easy
- **核心考点**: 二叉树 / 深度优先搜索 (DFS) / 后序遍历 (Post-order Traversal) / 剪枝优化

## 1. 题目描述

给定一个二叉树，判断它是否是高度平衡的二叉树。

> **高度平衡二叉树定义**：一个二叉树每个节点的左右两个子树的高度差的绝对值不超过 1。

## 2. 核心原理：为什么选择后序遍历（自底向上）？

1. **天然依赖子问题**：
   - 节点的高度：$\max(\text{左子树高度}, \text{右子树高度}) + 1$
   - 节点的平衡性：$\vert{}\text{左子树高度} - \text{右子树高度}\vert{} \le 1$
   - 父节点必须等待左右子树返回高度后才能进行计算，这与**后序遍历（左 $\to$ 右 $\to$ 根）**的执行顺序完全一致。
2. **避免重复计算**：
   - 自顶向下（前序遍历）会在每个节点向下重复遍历子树，导致 $O(N^2)$ 复杂度。
   - 自底向上（后序遍历）在回溯过程中一次性完成高度计算与平衡校验，保证每个节点仅被访问一次，时间复杂度降至 $O(N)$。
3. **快速失败剪枝（Fail-Fast）**：
   - 若子树已失衡，返回特殊标记 `-1`。
   - 上层调用检测到 `-1` 时立即终止后续递归并向上传递，避免遍历无效分支。

## 3. 代码实现

### 解法一：自底向上后序遍历（最优解，推荐）

```python
# Definition for a binary tree node.
# class TreeNode:
#     def __init__(self, val=0, left=None, right=None):
#         self.val = val
#         self.left = left
#         self.right = right

class Solution:
    def isBalanced(self, root: Optional[TreeNode]) -> bool:
        def check_height(node: Optional[TreeNode]) -> int:
            if not node:
                return 0
            
            # 1. 递归计算左子树高度
            left_h = check_height(node.left)
            if left_h == -1:  # 左子树已失衡，直接剪枝
                return -1
            
            # 2. 递归计算右子树高度
            right_h = check_height(node.right)
            if right_h == -1:  # 右子树已失衡，直接剪枝
                return -1
            
            # 3. 校验当前节点是否失衡
            if abs(left_h - right_h) > 1:
                return -1
            
            # 4. 返回当前子树的真实高度
            return max(left_h, right_h) + 1
        
        return check_height(root) != -1
```

- **时间复杂度**: $O(N)$，每个节点仅被访问一次。
- **空间复杂度**: $O(H)$，取决于递归调用栈深度（平衡树为 $O(\log N)$，退化为链表时最坏为 $O(N)$）。

### 解法二：自顶向下前序遍历（基础解法，存在重复计算）

```python
class SolutionTopDown:
    def isBalanced(self, root: Optional[TreeNode]) -> bool:
        if not root:
            return True
        
        def get_height(node: Optional[TreeNode]) -> int:
            if not node:
                return 0
            return max(get_height(node.left), get_height(node.right)) + 1
        
        # 检查当前根节点
        left_h = get_height(root.left)
        right_h = get_height(root.right)
        if abs(left_h - right_h) > 1:
            return False
        
        # 递归检查子节点
        return self.isBalanced(root.left) and self.isBalanced(root.right)
```

- **时间复杂度**: $O(N^2)$（最差情况），退化链表时每层均需重新遍历整条子链。
- **空间复杂度**: $O(N)$，递归调用栈深度。

自顶向下（Top-Down）之所以会退化到 $O(N^2)$，是因为发生了严重的“重复遍历与重复计算”。

最能说明问题的就是最极端的单链表（一条线退化）场景：

### 1. 极端场景：退化为单链表

假设二叉树退化成了一条向右延伸的链表，共 $N$ 个节点：
$$1 \to 2 \to 3 \to \dots \to N$$

当执行自顶向下的代码时：

* **站在节点 1**：
  * 调用 `get_height(1)` 算高度，必须把底下所有的 $N$ 个节点全遍历一遍 $\to$ 耗费 $N$ 次操作。
* **递归走到节点 2**：
  * 调用 `get_height(2)` 算高度，又把底下剩余的 $N-1$ 个节点全遍历一遍 $\to$ 耗费 $N-1$ 次操作。
* **递归走到节点 3**：
  * 调用 `get_height(3)` 算高度，把底下剩余的 $N-2$ 个节点全遍历一遍 $\to$ 耗费 $N-2$ 次操作。
* $\dots$
* **递归走到节点 $N$**：
  * 调用 `get_height(N)` 算高度 $\to$ 耗费 $1$ 次操作。

### 2. 数学求和：这就是高斯等差数列

把每一层消耗的操作次数加起来：

$$\text{总操作数} = N + (N - 1) + (N - 2) + \dots + 2 + 1$$

利用等差数列求和公式：

$$\sum_{k=1}^{N} k = \frac{N(N + 1)}{2} = \frac{N^2 + N}{2}$$

根据大 $O$ 渐进表示法，忽略常数项和低阶项，时间复杂度就是 $O(N^2)$。

### 3. 一句话核心本质

自顶向下的逻辑是：“领导（上层节点）每次算自己高度，都要把底下所有人重新点名一遍；轮到副领导（下一层）时，又把底下的人再重新点名一遍。”

这种层层向下、重复点名的做法，导致总计算量直接膨胀成了 $O(N^2)$。

## 4. 两种解法对比

| 维度 | 自顶向下 (Top-Down) | 自底向上 (Bottom-Up) |
| :--- | :--- | :--- |
| **遍历顺序** | 前序遍历（根 $\to$ 左 $\to$ 右） | 后序遍历（左 $\to$ 右 $\to$ 根） |
| **时间复杂度** | $O(N^2)$ | **$O(N)$** |
| **重复计算** | 严重（上层节点重复扫描下层） | 无（每个节点只计算一次高度） |
| **剪枝效率** | 弱 | 强（遇到 `-1` 立即级联退出） |

# 778. Swim in Rising Water

- **LeetCode 链接**: [Swim in Rising Water](https://leetcode.com/problems/swim-in-rising-water/)
- **难度**: Hard
- **核心考点**: 图论 / 优先队列 (Min-Heap) / 类似 Dijkstra 的最短路 / 二分查找 + BFS

## 1. 题目描述

在一个 $n \times n$ 的整数网格 `grid` 中，每个平台的高度由 `grid[i][j]` 表示。

你从平台 `(0, 0)` 出发，目标是到达右下角的平台 `(n-1, n-1)`。

- 在时刻 $t$，你只能游泳到达高度 $\le t$ 的相邻平台（上下左右）。
- 只要相邻平台均处于水下（高度 $\le t$），你可以瞬间游过任意数量的平台，耗时为 0。
- 返回**从 `(0, 0)` 到达 `(n-1, n-1)` 所需的最少等待时间 $t$**。

## 2. 核心思路分析

### 本质理解：最小瓶颈路径（Minimax Path）
到达终点的代价不是路径权值之和，而是整条路径上的**“最高格子海拔（水位最大值）”**。我们需要在所有连通起点与终点的路径中，找一条**“最大海拔最小”**的路径。

- **优先队列 (Min-Heap / Dijkstra 变体) —— 最优推荐**：
  - 维护一个最小堆，存储三元组 `(到达该点所需的最低水位, r, c)`。
  - 每次贪心地从堆中弹出**当前水位最低**的格子进行拓展。
  - 走到相邻格子 $(nr, nc)$ 时，到达新格子所需的水位为：
    new_time = max(time, grid[nr][nc])
  - **第一次从堆中弹出终点 `(n-1, n-1)` 时，此时记录的水位即为全局最小所需时间**。

## 3. 代码实现 (Python3)

```python
import heapq
from typing import List

class Solution:
    def swimInWater(self, grid: List[List[int]]) -> int:
        n = len(grid)
        # 记录已访问过的节点，避免重复走回头路
        visited = set([(0, 0)])
        
        # 最小堆：(当前路径上的最大水位, row, col)
        # 初始时必须至少等待水位涨到起点高度 grid[0][0]
        min_heap = [(grid[0][0], 0, 0)]
        
        directions = [(0, 1), (1, 0), (0, -1), (-1, 0)]
        
        while min_heap:
            time, r, c = heapq.heappop(min_heap)
            
            # 首次从堆顶弹出终点，该水位即为全局最优解
            if r == n - 1 and c == n - 1:
                return time
            
            for dr, dc in directions:
                nr, nc = r + dr, c + dc
                
                # 检查边界与是否已访问
                if 0 <= nr < n and 0 <= nc < n and (nr, nc) not in visited:
                    visited.add((nr, nc))
                    # 新路径上的最大水位 = max(当前路径最大水位, 新格子海拔)
                    new_time = max(time, grid[nr][nc])
                    heapq.heappush(min_heap, (new_time, nr, nc))
                    
        return -1
```

## 4. 复杂度分析

- **时间复杂度**: $O(N^2 \log N)$。
  - 网格总共有 $N^2$ 个节点，每条边最多被访问一次。
  - 每个节点最多进出优先队列一次，每次堆操作耗时 $O(\log(N^2)) = O(2 \log N) = O(\log N)$。
- **空间复杂度**: $O(N^2)$。
  - `visited` 集合与最小堆最多容纳 $N^2$ 个元素。
 
### 为什么这道题要用最小堆（Min-Heap）？

这道题的本质是**“谁先把路给淹了，我就先往谁那里走”**。

如果不使用最小堆，而是使用普通队列（普通 BFS）或递归（DFS），遍历过程会遇到根本性的困难：

1. **普通 BFS 为什么不行？（步数少 $\neq$ 水位低）**
   - 普通 BFS 采用先进先出（FIFO）队列，它的特点是**“按步数扩散”**：
     - 先走 1 步能到的所有格子；
     - 再走 2 步能到的所有格子……
   - 但在本题中，**走得近不代表水位低**：
     - 离起点走 1 步的格子海拔是 `50`。
     - 离起点走 5 步的绕路路径海拔全都在 `1 ~ 3`。
   - 如果用普通 BFS，算法会被困在“步数少但海拔奇高”的格子里，无法判断哪条路径能以更低的水位通关。

2. **最小堆在做什么？（模拟真实的水位上涨）**
   - 最小堆（Min-Heap）把“按步数遍历”变成了**“按真实水位从低到高遍历”**。
   - 把整个网格想象成注水过程：
     - 随着时间推进，水是从**最低的洼地**开始蔓延的。
     - 每次从最小堆里 `heappop` 出来的，永远是**当前所有可连通边界上海拔最低的那个格子**。
     - 这保证了遍历顺序是：**优先把所有好走的、海拔低的路全部探完**。只有当低海拔的路全部被山峰挡死时，堆顶才会浮现出更高的山峰（水位被迫上涨）。

3. **最关键的好处：首次到达即最优**
   - **普通搜索**：找到一条通往终点的路后，无法确定它是不是最优解，必须把所有可能的路径全部穷举完才能得出结论。
   - **最小堆（Dijkstra 原理）**：
     - 每次都在探索**全局代价最小（水位最低）**的下一步。
     - **当终点第一次从堆顶被弹出的那一瞬间，可以 100% 确定：其他任何还没走完的路径，其所需的水位都已经 $\ge$ 当前水位了。**
     - 此时可以直接 `return` 结束程序，避免遍历所有分支。

### 3x3 矩阵 Dry Run 演示

用一个最直观的 $3 \times 3$ 例子来一步一步 Dry Run（手动模拟运行），看看最小堆是怎么做到“先逛低洼地，直到被山挡死才被迫涨水”的。

#### 测试地图

```text
[  0,   1,  50 ]
[ 50,   2,  50 ]
[ 50,   3,   4 ]
```

- **起点**：左上角 `(0, 0)`，海拔 0。
- **终点**：右下角 `(2, 2)`，海拔 4。
- 周围一圈全都是高度 50 的高山。
- 中间藏了一条低洼小路：$0 \to 1 \to 2 \to 3 \to 4$。

### Step-by-Step 模拟执行

#### 初始状态
- 把起点入堆：`min_heap = [(0, 0, 0)]` （格式：`[水位, 行, 列]`）
- `visited = {(0, 0)}`

#### 第 1 轮
- **弹出堆顶**：`(0, 0, 0)`，当前水位 = 0。
- **看四周邻居**：
  - 右边 `(0, 1)` 海拔是 1 $\to$ 入堆 `(max(0, 1), 0, 1) = (1, 0, 1)`
  - 下面 `(1, 0)` 海拔是 50 $\to$ 入堆 `(max(0, 50), 1, 0) = (50, 1, 0)`
- **当前堆里有的选项**：`[(1, 右), (50, 下)]`
- **堆的自动选择**：**1 最小！** 绝对不碰 50。

#### 第 2 轮
- **弹出堆顶**：`(1, 0, 1)`，当前水位 = 1。
- **看四周邻居**：
  - 右边 `(0, 2)` 海拔是 50 $\to$ 入堆 `(max(1, 50), 0, 2) = (50, 0, 2)`
  - 下面 `(1, 1)` 海拔是 2 $\to$ 入堆 `(max(1, 2), 1, 1) = (2, 1, 1)`
- **当前堆里有的选项**：`[(2, 中间), (50, 下), (50, 右上)]`
- **堆的自动选择**：**2 最小！** 依然无视所有的 50。

#### 第 3 轮
- **弹出堆顶**：`(2, 1, 1)`，当前水位 = 2。
- **看四周邻居**：
  - 左边 `(1, 0)` 已访问；右边 `(1, 2)` 是 50 $\to$ 入堆 `(50, 1, 2)`
  - 下面 `(2, 1)` 是 3 $\to$ 入堆 `(max(2, 3), 2, 1) = (3, 2, 1)`
- **当前堆里有的选项**：`[(3, 中下), (50, 下), (50, 右上), (50, 右中)]`
- **堆的自动选择**：**3 最小！** 堆顶永远把 50 压在最底下。

#### 第 4 轮
- **弹出堆顶**：`(3, 2, 1)`，当前水位 = 3。
- **看四周邻居**：
  - 左边 `(2, 0)` 是 50 $\to$ 入堆 `(50, 2, 0)`
  - 右边 `(2, 2)` 是 **终点 4** $\to$ 入堆 `(max(3, 4), 2, 2) = (4, 2, 2)`
- **当前堆里有的选项**：`[(4, 终点), (50, ...), (50, ...), (50, ...)]`
- **堆的自动选择**：**4 最小！**

#### 第 5 轮
- **弹出堆顶**：`(4, 2, 2)`
- **命中判断**：弹出的是右下角终点！直接 `return 4`。

### 为什么说“只有被挡死时才被迫涨水”？

假设上面那个例子里，终点 `(2, 2)` 的海拔不是 4，而是 **100** 呢？

1. 算法依然会一路顺畅地走完 $0 \to 1 \to 2 \to 3$（水位达到 3）。
2. 在 3 的时候，四周能走的只有：终点 100，以及四周一圈之前扔进去的 50。
3. 堆里此时剩下的元素是：`[50, 50, 50, 50, 100]`。
4. **低洼路全没了（被 100 和 50 封死）**：堆顶这时候才会把 **50** 浮上来，算法被迫把水位提升到 50，开始去试探那些原本不想碰的高山。

> **核心结论**：最小堆像水流一样，永远只往阻力最小、地势最低的地方流，直到所有低洼处都被填满，水才会漫过更高的坎。


## 5. 易错点与关键细节

1. **起点初始代价不是 0**：如果起点 `grid[0][0] = 5`，即使一步不走也必须等水位涨到 5 才能下水，因此堆初始值为 `(grid[0][0], 0, 0)`。
2. **弹出终点才返回**：必须在 `heappop` 弹出终点时返回结果，不能在 `heappush` 入堆时提前判定，因为后入堆的路径可能具有更小的水位代价。

这套代码里的**“贪心”**主要体现在这一行：

```python
time, r, c = heapq.heappop(min_heap)
```

具体体现在以下两个层面：

1. **局部最优决策：每次只挑选“当前代价最小”的节点**
   - **普通搜索**：不管三七二十一，按顺序（先入先出或递归深度）去探路。
   - **贪心策略**：面对当前所有已经发现但还没探索的分支，永远只贪心地选择“到达所需水位最低”的那一个先走。
   - 只要眼前有水位为 1 的路，就坚决不去碰水位为 50 的路。
   - 这种“每一步都选眼前最好/最小的”行为，就是最典型的贪心选择性质。

2. **贪心成立的数学保证（单调不减性）**
   - 为什么这种“贪心”不会导致漏掉全局最优解？
   - 因为水位的更新公式是：`new_time = max(time, grid[nr][nc])`。
   - 路径上的水位只会保持不变或越来越大（单调不减），绝不可能越走水位反而变小。
   - 这意味着：如果堆顶当前弹出的水位是 $T$，那么堆里剩下那些水位 $\ge T$ 的候选路，之后不管怎么继续往前延伸，最终的水位也绝不可能小于 $T$。

**总结**
贪心就体现在：永远坚信“当前水位最低的分支最有希望以最小代价率先摸到终点”，从而通过 `heappop` 每次优先拓展它。第一次从堆顶摸到终点时，贪心策略直接锁定了全局最优解。

### 778. Swim in Rising Water：Cost 如何让 Min-Heap 达成全局最优

面试官问“Cost 怎么让 Min-Heap 达成全局最优”，核心考点在于 **Dijkstra 算法保证全局最优的数学证明（单调性与贪心选择性质）**。

回答时讲清以下 **3 层递进逻辑** 即可：

#### 1. Cost 的核心数学性质：单调不减（Monotonicity）

在这道题中，状态转移方程为：
$$\text{new\_cost} = \max(\text{current\_cost}, \text{grid}[nr][nc])$$

该公式具有严格的保序性：**沿途的 Cost 永远 $\ge$ 当前的 Cost**。
* 当前路径的 Cost 为 16，后续无论再走多少步，整条路径最终的 Cost 只能是 $\ge 16$，绝不可能降到 15。

#### 2. 核心证明：为什么节点出堆的瞬间即为最优解？

假设在某一轮循环中，堆顶弹出了节点 $U$，其记录的代价为 $\text{Cost}(U)$。

**证明：$\text{Cost}(U)$ 必定是起点到达节点 $U$ 的全局最小代价。**

使用**反证法**：
1. 假设存在另一条尚未探索完的替代路径也能到达 $U$，且其最终代价严格更小：
   $$\text{Cost}'(U) < \text{Cost}(U)$$
2. 该替代路径尚未延伸至 $U$，其前沿必存在至少一个节点 $V$ 仍停留在当前最小堆中未被弹出。
3. 既然本轮堆顶弹出的是 $U$ 而不是 $V$，根据最小堆的性质，必有：
   $$\text{Cost}(V) \ge \text{Cost}(U)$$
4. 根据 Cost 的**单调不减性**，从前沿节点 $V$ 继续向下探索到达 $U$，后续代价值只增不减：
   $$\text{Cost}'(U) \ge \text{Cost}(V)$$
5. 联立不等式：
   $$\text{Cost}'(U) \ge \text{Cost}(V) \ge \text{Cost}(U)$$
   这与假设 $\text{Cost}'(U) < \text{Cost}(U)$ **直接矛盾**。

**结论**：不存在任何潜在路径能以更小代价到达 $U$。**节点只要从堆顶弹出，其到达全局最优代价即被永久锁定。**

#### 3. 从“局部最优”到“全局最优”的闭环

* 堆顶弹出的每一个节点，在出堆瞬间均已被严格证明收敛于全局最小 Cost。
* 由数学归纳法可知，整个探索过程是按 Cost 递增顺序推进的。
* 当终点 `(n-1, n-1)` 第一次从堆顶被弹出时，到达终点的全局最小代价直接确认，无需继续遍历剩余分支。

#### 面试标准答题话术（30 秒精炼总结）

> “因为我们定义的 Cost 转移方程 $\text{new\_cost} = \max(\text{cost}, \text{height})$ 满足**单调不减性（Monotonicity）**。  
> 堆中所有未被弹出的备选分支，其当前 Cost 都大于等于堆顶节点。由于单调性，这些分支未来继续延伸也绝不可能产生更小的 Cost。  
> 因此，**每次从 Min-Heap 堆顶弹出的节点，其到达代价必定是全局最优解**。当终点首次出堆时，即锁定了全局最小代价，无需遍历所有剩余分支。”

### 为什么选 Dijkstra 而不是“单线贪心”：算法选型与决策思维

**Dijkstra 本身就是一种纯正的贪心算法（Greedy Algorithm）。**  
面试时常说的“不要用贪心”，通常指的是**“单线盲目贪心”（Single-path Greedy / 局部贪心走单路）**。

#### 1. 概念厘清：“狭义贪心” vs “Dijkstra（广义贪心）”

| 对比维度 | 盲目贪心（狭义贪心） | Dijkstra / Min-Heap（基于前沿面的贪心） |
| :--- | :--- | :--- |
| **搜索机制** | **只走一条路**。每一步在当前节点的邻居里挑一个最好的，直接抛弃其他邻居。 | **多线并行维护**。把所有已发现但未探索的邻居扔进堆，由堆顶决定下一个推进哪条线。 |
| **容错能力** | **零容错**。眼前选了低洼地，后面一旦遇到高山就全盘皆输。 | **自动切换战线**。当前线路如果代价变高，堆会自动切回另一条潜在线路。 |
| **状态回溯** | **无回溯**，一条路走到黑（如果走不通就必须退回，退化成 DFS）。 | **无需回溯**，所有历史前沿分支都在堆中并发备选。 |
| **本质区别** | 仅考虑**局部一步**的最优。 | 考虑**全局所有已知前沿路径**的最小代价。 |

#### 2. 为什么 778 题必须选 Dijkstra，而不能用“单线贪心”？

用最直接的场景证明为什么单线贪心必败：

```text
起点 (0) ---> 邻居 A (水位 1)  ---> 终点前挡着一座山 (水位 100)
         ---> 邻居 B (水位 10) ---> 一路平坦直达终点 (水位 10)
```

* **如果用单线贪心**：站在起点看，$1 < 10$，算法立刻选 A，抛弃 B。结果在 A 后面被迫承受 100 的代价。
* **如果用 Dijkstra**：
  1. A(`1`) 和 B(`10`) 都在堆里。
  2. 先试探 A，发现后面的路暴涨到 100，入堆。
  3. 堆顶立刻切换到 B(`10`)，因为 $10 < 100$。
  4. 最终以代价 10 顺利通关。

**Dijkstra 成功的核心就在于：它贪的不是“下一步迈向哪”，而是“全场所有备选路径中，哪一条目前的总代价最低”。**

### 3. 什么时候才真正适合用“纯粹的狭义贪心”？

不需要堆来维护多条前线、每一步直接做死决定的纯贪心算法，仅在满足以下场景时成立：

* **决策具有绝对不可逆的包含关系（区间调度）**  
  * 例如 **LeetCode 435. 无重叠区间**：永远选结束时间最早的活动。因为结束越早，留给后面的时间窗口严格更大（数学置换法成立），选它绝对不会劣于选其他选项。
* **资源分配无碎片浪费（排序匹配 / 双指针）**  
  * 例如 **LeetCode 455. 分发饼干**：大饼干给大胃口，直接排序后单向双指针遍历。每个选择都不会破坏后续的最优子结构。
* **树形或拓扑单向流（无分叉竞争）**  
  * **最小生成树的 Kruskal 算法**：利用拟阵性质，直接对所有边排序，由小到大只要不形成环就直接纳为树边。

### 4. 面试总结：四步决策思维树

面试遇到优化 / 路径类问题时，按以下顺序层层筛选：

1. **能否一步做死决策？（单线贪心 / 排序遍历）**  
   * 看是否存在数学替换证明（Exchange Argument）。如果眼前最好的选择绝不会锁死未来空间，直接单线贪心。
2. **状态是否单调且有分支竞争？（Dijkstra / 优先队列）**  
   * 边权非负，或者代价为 $\max$ 单调递增。有多条路径竞争，必须用堆来调度全局最前沿。
3. **选择之间互相制约、有容量限制？（动态规划 DP）**  
   * 比如 0-1 背包、股票买卖。当前选择会占用固定配额，导致未来无法挑选其他组合，必须枚举状态重叠子问题。
4. **无后效性被彻底打破、必须求全部可行方案？（DFS 回溯）**  
   * 需要打印所有路径，必须暴力尝试每一种可能并撤销现场

这道题是 **LeetCode 1631. 最小体力消耗路径 (Path With Minimum Effort)**。

如果你记得名字里带 “Distance”，那大概率是把它和 **LeetCode 505. 迷宫 II (The Maze II / 最短距离)**，或者它在各家题解里的经典别名 **“Shortest Distance / Minimax Path”** 记混了；但跟 778 **本质完全是孪生兄弟、算法一模一样** 的就是 **1631 题**。

### 1. 为什么说 1631 和 778 是孪生题？

两道题的骨架和考点 **100% 一模一样**，都属于 **“瓶颈最短路（Bottleneck / Minimax Shortest Path）”**：

* **778. 水位上升 (Swim in Rising Water)**：
  * **Cost 定义**：沿途经过格子的最高绝对海拔。
  * **转移方程**：`new_cost = max(current_cost, grid[nr][nc])`
* **1631. 最小体力消耗路径 (Path With Minimum Effort)**：
  * **Cost 定义**：沿途连续两格之间的最大绝对高度差（Effort）。
  * **转移方程**：
    * `diff = abs(heights[r][c] - heights[nr][nc])`
    * `new_cost = max(current_cost, diff)`

除了算单步高度差多了一句取绝对值减法之外，Min-Heap、visited 判定、单调性证明、出堆即最优的代码写出来一字不差。

### 2. 如果名字里必须带 “Distance” 的相关 Dijkstra 变体

如果是明确带 Distance 字眼的题目，且同样运用了 Dijkstra / Cost 思想的，是下面两道高频题：

* **LeetCode 505. 迷宫 II (The Maze II)**
  * 英文描述里核心就是算 Shortest Distance。
  * 球在滚碰到墙之前不能停下，每滚一格步数累加，用 Min-Heap 按累计滚过的距离（Distance）做 Dijkstra。
* **LeetCode 787. K 站中转内最便宜的航班 (Cheapest Flights Within K Stops)**
  * 题目虽然叫 Flights，但标准图论原型就是 Shortest Path with Distance/Stop Constraints。

### 3. “同一解法群”的标准通解模板

778 和 1631 在面试中被称为“模板姊妹题”，它们共享同一套解题大招库：

1. **优先队列 / Dijkstra**：最直接，也是前面证明过的“单调性 + 反证法”。
2. **二分查找 + 普通 BFS / DFS**：把答案二分猜一个值 $mid$，看能否走通。
3. **并查集 (Union-Find)**：把所有相邻的边按 Cost 排序，从小到大连通起点和终点。

### 为什么 778 与 1631 考虑的是 Cost（瓶颈代价）？

这两道题之所以引入特殊的 Cost（即瓶颈代价），是因为它们的优化目标根本不是传统的**“累加总和（Sum）”**，而是**“木桶效应（Minimax / 瓶颈最短路）”**。

在生活和算法中，问题的目标可以分为两类：

#### 1. 传统最短路：拼“总开销” ($\sum w$)
* **场景**：比如地图导航、网购运费。
* **逻辑**：每多走一步，路程或费用就累加一次（$\text{Cost} = w_1 + w_2 + w_3 + \dots$）。
* **特点**：走得越远，总代价通常越大。

#### 2. 778 与 1631：拼“最坏的那一步（瓶颈）” ($\max$)
这两题关心的不是你走了多少步、总共消耗了多少，而是**整条路上遇到的“最大难关”是什么**：

* **778（水位上升）**：
  * **物理意义**：水位的上涨由全场最高的那座山决定。
  * **为什么看 Cost**：如果你在路上翻越了一座 100 米的高山，哪怕前面 99 步全都是 0 米的平地，水也必须涨到 **100** 你才能过得去。整条路的生死由那个“最高峰”锁死。
* **1631（最小体力消耗）**：
  * **物理意义**：体力的极限由最陡峭的那段绝壁决定。
  * **为什么看 Cost**：你走 1000 步平路不费力，但只要中间有一个 50 米的垂直峭壁需要爬，你当下的最大体力消耗就是 **50**。你不是累死在平路上，而是累死在那一步最难的坎上。

#### 3. 为什么必须用 Cost 来驱动 Min-Heap？

正是因为代价由**局部最大值（Bottleneck）**决定，算法才必须用 `new_cost = max(current_cost, next_step)` 来实时监控每一条分支的“最坏情况”。

* **Min-Heap 的直觉**：它永远优先处理当前“最轻松（最大难关最低）”的队伍。
* **避免误判**：如果不把这个 Cost 挂在堆里作为排序依据，算法就会像普通 BFS 一样盲目去数步数，从而被“看起来近、但有一座 100 米大山”的死路给坑害。
