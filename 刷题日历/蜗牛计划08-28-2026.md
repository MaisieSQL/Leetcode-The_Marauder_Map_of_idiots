# LeetCode 104. Maximum Depth of Binary Tree (二叉树的最大深度)

## 📝 题目描述 (Description)
给定一个二叉树的根节点 `root`，找出并返回其**最大深度**[cite: 4]。
二叉树的最大深度是指从根节点到最远叶子节点的最长路径上的节点数（叶子节点是指没有子节点的节点）[cite: 4]。

---

## 🛠️ 多种解法与代码实现 (Multiple Solutions)

### 方法一：递归流（自底向上 DFS / 甩手掌柜法）── 最经典、最优雅
#### 💡 核心直觉
把你自己当成大老板（根节点），你把左右副总叫来，让他们各自汇报左右子树的最大深度。你只需要挑出最大的一边，然后加上你自己的那一层（`+ 1`）即可[cite: 4]。

#### 💻 Python3 代码实现
```python
# Definition for a binary tree node.
# class TreeNode:
#     def __init__(self, val=0, left=None, right=None):
#         self.val = val
#         self.left = left
#         self.right = right


class Solution:

  def maxDepth(self, root: Optional[TreeNode]) -> int:
    # 1. 递归出口：空节点深度为 0
    if not root:
      return 0

    # 2. 递归获取左右子树的最大深度
    left_depth = self.maxDepth(root.left)
    right_depth = self.maxDepth(root.right)

    # 3. 左右取最大值，并加上当前根节点所在的这一层
    return max(left_depth, right_depth) + 1
```

### 方法二：广度优先搜索流（BFS / 层序遍历计数）── 工业级队列迭代
#### 💡 核心直觉
使用队列（Queue）进行层序遍历。每一层扫过去时，用 `step` 计数器记录层数。整棵树被剥完几层，最大深度就是几。

#### 💻 Python3 代码实现
```python
from collections import deque


class Solution:

  def maxDepth(self, root: Optional[TreeNode]) -> int:
    if not root:
      return 0

    queue = deque([root])
    depth = 0

    while queue:
      level_size = len(queue)
      for _ in range(level_size):
        node = queue.popleft()
        if node.left:
          queue.append(node.left)
        if node.right:
          queue.append(node.right)
      # 每一层处理完，深度 +1
      depth += 1

    return depth
```

### 方法三：前序遍历迭代流（DFS 显式栈 + 状态追踪）
#### 💡 核心直觉
用显式栈模拟递归过程，在栈里同时存储节点和它当前对应的深度。边往下走边用全局变量或比对刷新最大深度。

#### 💻 Python3 代码实现
```python
class Solution:

  def maxDepth(self, root: Optional[TreeNode]) -> int:
    if not root:
      return 0

    stack = [(root, 1)]
    max_d = 0

    while stack:
      node, depth = stack.pop()
      if node:
        max_d = max(max_d, depth)
        if node.left:
          stack.append((node.left, depth + 1))
        if node.right:
          stack.append((node.right, depth + 1))

    return max_d
```

复杂度核验 (Complexity Analysis)
- 时间复杂度：$O(N)$ —— 其中 $N$ 是二叉树的节点总数。每一个节点在遍历过程中都恰好被访问一次。
- 空间复杂度：$O(H)$ —— 其中 $H$ 是树的高度。主要消耗在递归调用栈（或 BFS 队列）上。在最坏情况下（链状树），空间复杂度为 $O(N)$；在平衡二叉树中，空间复杂度为 $O(\log N)$。

# LeetCode 17. Letter Combinations of a Phone Number (电话号码的字母组合)

## 📝 题目描述 (Description)
给定一个仅包含数字 `2-9` 的字符串，返回所有它能表示的字母组合。答案可以按**任意顺序**返回。
给出数字到字母的映射如下（与电话按键相同）。注意 1 不对应任何字母。

- `2`: "abc"
- `3`: "def"
- `4`: "ghi"
- `5`: "jkl"
- `6`: "mno"
- `7`: "pqrs"
- `8`: "tuv"
- `9`: "wxyz"

### 💡 示例 1:
- **Input**: `digits = "23"`
- **Output**: `["ad","ae","af","bd","be","bf","cd","ce","cf"]`

## 🧠 一、 核心心法与物理直觉 (Backtracking Core)
1. **树形结构的诞生**：
   - 如果输入是 `"23"`，第一位是 `'2'`（对应 `'a', 'b', 'c'`），第二位是 `'3'`（对应 `'def'`）。
   - 这就像是一个多叉树：根节点向下分 3 条叉，每个子节点再向下分多条叉。我们要找的就是从根节点走到所有叶子节点的全路径。
2. **回溯三部曲（选择 $\rightarrow$ 递归 $\rightarrow$ 撤销）**：
   - **选择**：把当前候选字母加入临时路径（`path.append(letter)`）。
   - **递归**：带着新路径去处理下一个数字（`backtracking(index + 1, path)`）。
   - **撤销**：从深处返回后，立刻弹出刚才的字母（`path.pop()`），尝试同层的下一个候选分支。

## 💻 二、 满分通关代码 (Python 3)

```python
class Solution:

  def letterCombinations(self, digits: str) -> list[str]:
    # 边界防御：如果输入的数字串为空，直接返回空列表
    if not digits:
      return []

    res = []
    # 💡 键必须是字符串 str，因为 digits[index] 拿出来的是字符
    digitMap = {
        '2': 'abc',
        '3': 'def',
        '4': 'ghi',
        '5': 'jkl',
        '6': 'mno',
        '7': 'pqrs',
        '8': 'tuv',
        '9': 'wxyz',
    }

    def backtracking(index, path):
      # 递归出口：如果路径长度等于输入的数字长度，说明拼成了一个完整组合
      if index == len(digits):
        res.append(''.join(path))
        return

      curr_digit = digits[index]
      char = digitMap[curr_digit]

      for i in char:
        path.append(i)  # 1. 做选择
        backtracking(index + 1, path)  # 2. 递归处理下一层
        path.pop()  # 3. 撤销选择

    backtracking(0, [])
    return res
```

### 三、 复杂度核验 (Complexity Analysis)
- **时间复杂度**：$O(4^N * N)$ —— 其中 $N$ 是输入数字字符串 `digits` 的长度。在最坏情况下（比如数字全是 7 或 9，对应 4 个字母），每个数字有 4 种分支，总叶子节点数最多可达 $4^N$ 个，每次把路径拼成字符串需要 $O(N)$ 的时间。
- **空间复杂度**：$O(N)$ —— 主要消耗在递归调用栈的深度（最大深度为 $N$）以及临时存储路径的 `path` 空间上。

# 为什么“什么都是回溯算法”？—— 算法世界的底层物理直觉

在刷题的过程中，你可能会有一种强烈的感受：怎么遇到组合、排列、分割、甚至网格搜索，最后全都是回溯算法（Backtracking）？

## 1. 为什么“什么都是回溯算法”？

因为计算机本质上是一个“憨憨”。它无法像人类一样一眼看出最优解，面对一个复杂问题时，它只能做一件事：**穷举（Brute Force）**。

而“穷举”在物理上长什么样？
* 它长得就像一棵**巨大的决策树（Decision Tree）**。
* 你站在根节点，面对好几个分叉（比如选 A、选 B 还是选 C）。
* 你选了 A 之后，走到下一层，又面对新的分叉……
* **回溯算法，就是计算机在树形结构上进行“深度优先搜索（DFS）+ 现场恢复”的唯一物理动作。**

只要一道题符合下面几个特征，它就**注定**是回溯算法：
1. **要求你求出“所有可能的解”**（而不是只要一个最大值或最小值）。
2. **需要做多轮选择**（比如 17 题选字母，473 题火柴拼正方形要决定每根火柴给哪条边）。
3. **一条路走到黑之后，发现走不通或已经搜完，必须“退回来”换一条路走。**

## 2. 拿 473 题（火柴拼正方形）来当沙盘

咱们看看 473 题（Matchsticks to Square）在干什么：
* 给你一堆长度不同的火柴，让你把它们拼成一个完美的正方形（正方形有 4 条边）。
* **你的选择**：对于每一根火柴，你有 4 个去处 —— 它可以放在第 1 条边、第 2 条边、第 3 条边，还是第 4 条边？
* 这不就是个标准的 **4 叉树** 吗？
  * 第一根火柴：尝试放第 1 条边 ➔ 递归到第二根火柴……
  * 如果某一条边的长度超标了（剪枝），或者整条树走完发现拼不成：**撞墙了，退回上一步（`pop` / 恢复现场），把这根火柴从当前边拿出来，换到下一条边去试试！**

你看，**“做选择 ➔ 递归探路 ➔ 撤销选择（恢复现场）”**，这不就是 17 题电话号码背后的那套核心骨架吗？它们骨子里干的是一模一样的事情！

## 3. 回溯算法的“万能皮肤”

如果把算法题比作网游，**回溯算法就是那套永远换不掉的“底层骨骼模型”**，而其他题目只是换了件“皮肤”：
* **皮肤 A（LeetCode 17 题）**：每一层从数字对应的字母里选一个。
* **皮肤 B（LeetCode 473 题）**：每一层把火柴分给 4 条边。
* **皮肤 C（全排列 / 子集问题）**：每一层决定选或不选某个元素。

所以，你觉得“怎么什么都是回溯”，是因为**当题目要求你探索所有可能、寻找排列组合方案时，回溯算法是唯一的物理通解**。

# LeetCode 473. Matchsticks to Square (火柴拼正方形)

## 📝 题目描述 (Description)
你将得到一个整数数组 `matchsticks` ，其中 `matchsticks[i]` 是第 `i` 个火柴的长度。你要使用**所有的火柴**，拼成一个正方形。
绝不能折断任何一根火柴，每根火柴都必须用到，且每一根只能用一次。

如果能够使正方形的四条边长度**相等**，返回 `true` ；否则，返回 `false` 。

### 💡 示例 1:
- **Input**: `matchsticks = [1,1,2,2,2]`
- **Output**: `true`
- **解释**: 能拼成一个边长为 2 的正方形，所有火柴都被用完。

## 🧠 一、 物理直觉与回溯核心 (Core Intuition & Backtracking)

1. **前置数学剪枝（Fast Fail）**：
   - 火柴总长度 `total_sum` 必须能被 4 整除。如果不能，直接返回 `false`。
   - 正方形的边长 `target = total_sum // 4`。如果数组里最大的单根火柴长度超过了 `target`，直接返回 `false`（因为没有任何一条边能装下它）。
   - **优化技巧**：为了让回溯更早地“撞墙”剪枝，我们把火柴数组**从大到小排序**。优先把长的火柴分配给边，能让不合法的分支极快地被砍掉！

2. **状态定义与选择树**：
   - 我们有 4 条边（可以用一个长度为 4 的数组 `buckets = [0, 0, 0, 0]` 来记录当前 4 条边的总长度）。
   - 对于每一根火柴，我们有 **4 种去处** —— 它可以放到第 0 条边、第 1 条边、第 2 条边，或者第 3 条边。
   - 这就是一棵标准的多叉树搜索：尝试放某条边 ➔ 递归下一根火柴 ➔ 失败后撤销（`pop` / 恢复长度），尝试下一条边。

## 💻 二、 工业级 Python3 满分代码 (Solution)

```python
from typing import List

class Solution:

  def makesquare(self, matchsticks: List[int]) -> bool:
    # ------------------ [1. 前置预处理与边界判断] ------------------
    total_sum = sum(matchsticks)  # 时间: O(N) | 空间: O(1)
    if total_sum % 4 != 0:  # 时间: O(1) | 空间: O(1)
      return False

    target = total_sum // 4  # 时间: O(1) | 空间: O(1)
    matchsticks.sort(
        reverse=True
    )  # 时间: O(N log N) | 空间: O(N) 或 O(1) (取决于排序算法)

    if matchsticks[0] > target:  # 时间: O(1) | 空间: O(1)
      return False

    buckets = [0] * 4  # 时间: O(1) | 空间: O(1) (固定大小为 4 的数组)

    # ------------------ [2. 回溯递归核心函数] ------------------
    def backtrack(index: int) -> bool:
      # 递归出口：触发 N 次后达到叶子节点
      if index == len(matchsticks):  # 时间: O(1) | 空间: O(1)
        return (
            buckets[0] == target
            and buckets[1] == target
            and buckets[2] == target
            and buckets[3] == target
        )  # 时间: O(1) | 空间: O(1)

      # 尝试放置到 4 个桶中
      for i in range(4):  # 循环 4 次：O(1)
        if buckets[i] + matchsticks[index] > target:  # 时间: O(1) | 空间: O(1)
          continue

        buckets[i] += matchsticks[index]  # 时间: O(1) | 空间: O(1)

        # 核心递归调用：递归树深度最多为 N
        if backtrack(index + 1):  # 递归调用栈空间: 每层 O(1)，最大深度 N -> O(N)
          return True

        buckets[i] -= matchsticks[index]  # 时间: O(1) | 空间: O(1)

        if buckets[i] == 0:  # 时间: O(1) | 空间: O(1)
          break

      return False

    # ------------------ [3. 启动回溯入口] ------------------
    return backtrack(0)  # 整体最坏时间: O(4^N) | 整体空间: O(N)
```

### 三、 复杂度核验 (Complexity Analysis)
- **时间复杂度**：$O(4^N)$ —— 其中 $N$ 是火柴的数量。在最坏情况下，每一根火柴都有 4 个边可以选择分配。但由于加入了“从大到小排序”与“超标剪枝”、“空桶跳过”等强力优化，实际运行速度远低于理论最大值。
- **空间复杂度**：$O(N)$ —— 主要消耗在回溯递归调用栈的最大深度（最深为火柴总数 $N$），而记录 4 条边状态的辅助数组只占用 $O(1)$ 的常数空间。

# LeetCode 473. Matchsticks to Square (火柴拼正方形) —— 核心优化深度剖析

老铁，火眼金睛！咱们直接把这三大核心优化在代码里的**物理落脚点**一个个揪出来，看它们到底长在源码的哪个具体位置：

### 1. “从大到小排序”在哪？
在进入回溯递归之前，主函数一开始就对火柴数组进行了降序排列：
```python
matchsticks.sort(reverse=True)  # 👈 从大到小排序
```

- **物理意义**：把最长的火柴排在最前面。这样在回溯时，大火柴会优先被分配到桶里，能让不合法的分支在最浅的树层级就迅速超标撞墙，极大地提升了剪枝效率。

2. **“超标剪枝”在哪？**
在回溯的 `for` 循环里，每次尝试把当前火柴放进某一个桶（边）之前，有这样一处防御判断：
```python
for i in range(4):
  # 👈 核心超标剪枝：如果加上当前火柴超过了目标边长 target，直接跳过这个桶！
  if buckets[i] + matchsticks[index] > target:
    continue
```

- **物理意义**：正方形的每一条边最大长度不能超过 `target`。一旦超标，这条支路直接作废，无需再向下递归。

1. **“空桶跳过（去重剪枝）”在哪？**
2. **在回溯尝试失败、撤销选择（恢复现场）的紧下方，藏着最精妙的一刀**：
```python
# 做选择
buckets[i] += matchsticks[index]
if backtrack(index + 1):
  return True
# 撤销选择：恢复现场
buckets[i] -= matchsticks[index]
# 👈 核心空桶剪枝优化：如果当前桶长度为 0 且放这根火柴失败了，
# 说明后续再去尝试其他同样为空的桶没有任何意义（对称性剪枝），直接 break 结束循环！
if buckets[i] == 0:
  break
```

- **物理意义**：在初始状态下，4 个桶全都是空的（长度为 0）。如果把一根大火柴放进第 0 个空桶里，一路递归下去最后发现无解并退回了，那么接下来再去尝试放第 1 个空桶、第 2 个空桶……结果必然也是完全对称的死路。因此，尝试第一个空桶失败后，直接 `break` 终止同层对其他空桶的遍历，能砍掉大量重复的无效分支。

# LeetCode 698. Partition to K Equal Sum Subsets (划分为k个相等的子集)

## 📝 题目描述 (Description)
给定一个整数数组 `nums` 和一个正整数 `k`，找出是否有可能把这个数组分成 `k` 个非空子集，使得每个子集的元素和都相等。

### 💡 示例 1:
- **Input**: `nums = [4, 3, 2, 3, 5, 2, 1], k = 4`
- **Output**: `true`
- **解释**: 可以分成 4 个和为 5 的子集：`[5]`, `[1, 4]`, `[2, 3]`, `[2, 3]`。

### 💡 示例 2:
- **Input**: `nums = [1, 2, 3, 4], k = 3`
- **Output**: `false`

## 🧠 一、 物理直觉与核心剪枝 (Core Intuition & Pruning)

1. **动态桶容量定义**：
   - 目标单桶容量：`target = sum(nums) // k`。
   - 前置数学剪枝（Fast Fail）：
     - 若 `sum(nums) % k != 0`，连均分都无法做到，直接返回 `false`。
     - 若 `max(nums) > target`，说明存在单元素超过容积限制，无解直接返回 `false`。

2. **三大核心剪枝优化**：
   - **降序排序（从大到小）**：`nums.sort(reverse=True)`，把体积大的元素优先分配给桶，在递归树最浅层促成“超标撞墙”，砍掉庞大的无用子树。
   - **超标剪枝**：当 `buckets[i] + nums[index] > target` 时跳过。
   - **空桶对称性剪枝（去重）**：当 `buckets[i] == 0` 且递归失败退回时，说明将当前元素放入后续任意相同长度的空桶都会面临完全对称的死路，立刻使用 `break` 截断同层穷举。

## 💻 二、 Python3 满分标准代码 (Solution)

```python
from typing import List


class Solution:

  def canPartitionKSubsets(self, nums: List[int], k: int) -> bool:
    total_sum = sum(nums)

    # 1. 前置数学检查
    if total_sum % k != 0:
      return False

    target = total_sum // k
    nums.sort(reverse=True)  # 降序排序，大幅提高剪枝效率

    if nums[0] > target:
      return False

    buckets = [0] * k  # 开辟 k 个桶

    def backtrack(index: int) -> bool:
      # 递归出口：所有数字均已成功分配
      if index == len(nums):
        return True

      # 尝试将当前的数字放入 k 个桶中的某一个
      for i in range(k):
        # 剪枝 1：超标剪枝
        if buckets[i] + nums[index] > target:
          continue

        # 1. 做选择
        buckets[i] += nums[index]

        # 2. 递归探索
        if backtrack(index + 1):
          return True

        # 3. 撤销选择（恢复现场）
        buckets[i] -= nums[index]

        # 剪枝 2：空桶跳过/对称性剪枝
        if buckets[i] == 0:
          break

      return False

    return backtrack(0)
```

三、 复杂度核验 (Complexity Analysis)
- 时间复杂度：$O(k^N)$ —— 其中 $N$ 是数组 `nums` 的长度，$k$ 是子集数量。在理论最坏情况下，每个元素有 $k$ 种分配可能。通过降序排序、超标剪枝与空桶跳过，实际运算耗时远低于理论界限。
- 空间复杂度：$O(N)$ —— 主要消耗在系统递归调用栈的最大深度（最大深度为 $N$），分配的辅助桶数组消耗 $O(k)$ 空间。

# LeetCode 2707. Extra Characters in a String (字符串中的额外字符)

## 📝 题目描述 (Description)
给你一个下标从 `0` 开始的字符串 `s` 和一个单词字典 `dictionary` 。你需要将 `s` 分解成若干个互不重叠的子串，每个子串都在 `dictionary` 中出现过。`s` 可以有一些额外的字符，这些字符不包含在任何子串中。

请你设计一个算法，返回将 `s` 拆分后，**未包含在任何子串中的额外字符的最少数量**。

### 💡 示例 1:
- **Input**: `s = "leetscode", dictionary = ["leet","code","leetcode"]`
- **Output**: `1`
- **解释**: 将 `s` 拆分成 `"leet"` 和 `"code"`，剩下 1 个额外字符 `"s"`。

### 💡 示例 2:
- **Input**: `s = "sayhelloworld", dictionary = ["hello","world"]`
- **Output**: `3`
- **解释**: 将 `s` 拆分成 `"hello"` 和 `"world"`，剩下 3 个额外字符 `"say"`。

## 🧠 一、 物理直觉与动态规划核心 (Core Intuition & DP)

这道题是经典的**“带词典切分的最优化问题”**（类似于 LeetCode 139 单词拆分）。
- **物理直觉**：
  - 我们从左到右扫描字符串 `s`。对于每一个位置 `i`，我们面临两种选择：
    1. **当成额外字符放弃**：当前字符 `s[i-1]` 无法和前面的部分凑成字典里的任何单词，因此它是一个额外字符，最少额外字符数继承前一位 `dp[i-1] + 1`。
    2. **尝试作为某个单词的结尾匹配**：如果以当前位置结尾、往前截取的一段子串 `s[j:i]` 刚好在 `dictionary` 字典里，那么我们可以从状态 `dp[j]` 平移过来，不需要增加新的额外字符。
  - 这是一个标准的一维动态规划（DP）模型！

## 💻 二、 Python3 工业级满分代码 (Solution)

为了实现 $O(1)$ 的高效率字典单词查找，我们可以把 `dictionary` 放入一个哈希集合（`HashSet`）中：

```python
from typing import List


class Solution:

  def minExtraChar(self, s: str, dictionary: List[str]) -> int:
    n = len(s)
    word_set = set(dictionary)

    # dp[i] 表示字符串前 i 个字符（s[0...i-1]）在最优切分下最少包含多少个额外字符
    dp = [0] * (n + 1)

    for i in range(1, n + 1):
      # 默认选择：假设当前字符 s[i-1] 是额外字符，继承前一个状态 + 1
      dp[i] = dp[i - 1] + 1

      # 尝试往前回溯所有可能的单词起点 j，看看 s[j...i-1] 是否在词典中
      for j in range(i):
        if s[j:i] in word_set:
          # 如果子串在词典中，说明这段不需要额外字符，尝试更新更优解
          dp[i] = min(dp[i], dp[j])

    return dp[n]
```
- **时间复杂度**：$O(N^2 \times L)$ —— 其中 $N$ 是字符串 `s` 的长度，$L$ 是单词的最大长度。两层循环共计约 $N^2$ 次状态转移，每次切片和哈希表查找最长耗时与单词长度 $L$ 相关。对于数据范围而言性能极佳。
- **空间复杂度**：$O(N + M)$ —— 其中 $N$ 为 DP 数组的空间开销，$M$ 为哈希集合存储词典所有单词的内存开销。

老铁，这个问题极其深刻！你其实抓到了算法设计中最核心的“演化轴”：为什么有些题能从暴力的 Backtracking（回溯）一路进化到 DP（动态规划），甚至再进化到 Trie（前缀树）？

咱们把这三种方法的底层物理关系拆开，看清它们是怎么一步步演进的：

### 1. 为什么不用纯粹的 Backtracking (回溯)？
首先回答：能用 Backtracking 吗？能！但是直接用会暴毙（超时 TLE）。

#### 💡 暴力的 Backtracking 在干什么？
如果我们用纯回溯搜索 `s = "leetscode"`，在索引 `i` 处：
- **分支 A**：把当前字符当作额外字符（损耗 +1），递归 `dfs(i + 1)`。
- **分支 B**：枚举字典里每一个能和 `s[i...]` 匹配的单词，匹配成功后递归到下一个索引。

#### ❌ 致命痛点：爆炸级的“重复子问题”
假设 `s = "aaaaa..."`，字典里有 `["a", "aa", "aaa"]`：
- **路径 1**：先匹配 `"a"`，再匹配 `"a"` ➔ 此时到达索引 2。
- **路径 2**：直接匹配 `"aa"` ➔ 同样到达索引 2。
- **路径 3**：把前两个 `'a'` 都当作额外字符（`+1 +1`）➔ 还是到达索引 2。

在纯 Backtracking 下，计算机傻傻地针对“从索引 2 到结尾”这段子串，把后面所有的可能性重复搜索了 3 次！
随着字符串长度 $N$ 增加，这种指数级别的重叠搜索（$2^N$ 或更高）会让程序当场超时。

### 2. 为什么能进化到 DP（动态规划 / 记忆化搜索）？
当你给回溯算法加上一个备忘录（`memo` 数组或 `cache`）——即“只要我已经算过 `dfs(2)` 的答案，下次再遇到 `dfs(2)` 直接查表返回”，回溯就瞬间进化成了记忆化搜索（Top-down DP）！

进一步把它改写成自底向上的迭代形式，就是我们上一版写的 DP：

```python
# 状态定义：dp[i] 表示前 i 个字符的最少额外字符数
dp[i] = dp[i - 1] + 1  # 选择 1：当成额外字符
# 选择 2：如果 s[j:i] 在字典里，试着用 dp[j] 更新最小值
for j in range(i):
  if s[j:i] in word_set:
    dp[i] = min(dp[i], dp[j])
```

### 🎯 为什么能用 DP？
因为这道题满足 DP 的两大黄金性质：
1. **重叠子问题**：从位置 `i` 开始到末尾的最优解是固定不变的，前面的不同拼法只要最终停在 `i`，后面的解完全可以白嫖！
2. **无后效性**：我们只关心在索引 `i` 处“最少丢掉了几个字符”，至于前面到底具体用了哪些单词拼凑出来的，对后面的选择毫无影响。

### 3. 那为什么还要引入 Trie（前缀树）？
既然 DP 已经能拿满分了，前缀树（Trie）是来干嘛的？—— 它是来给 DP 提速的！

在普通 DP 中，我们检查子串是否在字典里需要这步操作：
```python
if s[j:i] in word_set: ...  # 👈 瓶颈在这！
```

每次切片 `s[j:i]` 并做哈希查找，如果子串比较长，截取字符串和哈希计算都有成本。并且为了找到合法的 `j`，我们需要把从 `0` 到 `i-1` 的所有位置都遍历一遍。

#### 🚀 Trie 的“时空隧道”剪枝优化：
如果我们将字典里的所有单词反向建一棵 Trie 树（或者从左到右匹配）：
当我们站在 `i` 位置往回倒查子串 `s[j...i-1]` 时：
- 我们从 Trie 的根节点开始，按照 `s[i-1]`, `s[i-2]`, `s[i-3]`... 的顺序在树上走。
- **物理优势**：一旦发现树的某个分支断了（比如字典里根本没有以这几个字符结尾的单词），后面的 `j` 根本不需要再循环试了，直接 `break` 终止内层循环！

### ⚔️ 三大方法全景对比

| 方法 | 核心机制 | 时间复杂度 | 命运 | 物理本质 |
| :--- | :--- | :--- | :--- | :--- |
| **纯 Backtracking** | 树形盲目穷举 | $2^N$ 或更高 | ❌ **超时 TLE** | 傻子穷举，疯狂重复计算相同子问题 |
| **DP (动态规划)** | 状态转移 + 消除重复计算 | $N^2$ 级别 | ✅ **满分 AC** | 用空间换时间，记住每个位置的最优解 |
| **DP + Trie (前缀树)** | DP 递推 + Trie 树前缀极速剪枝 | $N^2$ (内层更早熔断) | 🚀 **极致性能 AC** | 借用前缀树的“字符隧道”，发现没单词直接中断匹配 |

### 💡 终极结论
1. **Backtracking 是起点**：DP 本质上就是“带备忘录、消除了重复分支的 Backtracking”。
2. **DP 是解题主力**：利用无后效性和重叠子问题，把指数级搜索降维。
3. **Trie 是检索加速器**：在 DP 的匹配环节加入 Trie，能大幅剪掉那些不可能拼成单词的无效匹配分支。

你脑子里的这条算法升维演化路径（DFS ➔ Backtracking ➔ Cache / Memo ➔ DP ➔ Greedy）简直是算法精髓的“全家福”！每一次跃迁，都是人类为了对付计算机的“憨憨穷举”而开出的降维打击药方。

### 一、 结论先行：这道题能用贪心吗？

答案是：**不能盲目用“局部贪心”，但可以通过“全局贪心视角（DP 的本质）”来通关。**

如果在面试时，你想用传统的**纯贪心直觉**去解这道题（比如：“每走到一个地方，优先匹配字典里**最长的那个单词**，能匹配就立刻切下去”），**你会当场被测试用例无情打脸。**

### 二、 为什么“最长匹配贪心”会翻车？（反例剖析）

假设：
- 字符串 `s = "catsanddog"`
- 字典 `dictionary = ["cat", "cats", "sand", "dog"]`

#### 🏃‍♂️ 纯贪心（每一步贪图眼前最大长度）的走法：
1. 从下标 `0` 开始看，能匹配的最长单词是什么？是 `"cats"`（长度 4）。
2. 贪心算法大喜：“好！选最长的 `"cats"`！” ➔ 剩下的字符串变成了 `"anddog"`。
3. 从下标 `4`（即 `"a"`）开始看，剩下字符串 `"anddog"`，能匹配的最长单词是 `"dog"`（在末尾），把中间的 `"and"` 全都当成额外字符丢掉。
4. **贪心算出来的额外字符数**：中间浪费了 `"and"`（3个字符）。

#### 💡 真实的全局最优解：
1. 先选 `"cat"`（长度 3） ➔ 剩下 `"sanddog"`。
2. 再选 `"sand"`（长度 4） ➔ 剩下 `"dog"`。
3. 最后选 `"dog"`（长度 3）。
4. **全局最优的额外字符数**：**`0` 个额外字符！**

#### ❌ 贪心翻车的原因：
**局部的“最长匹配”并不代表全局的“额外字符最少”。** 贪心由于“目光短浅”（只看眼前能吃多大一块），常常会把后面更完美、能凑出无缝拼接的宝贵前缀给提前霍霍掉。这就是为什么这类求“全局最优化/最少代价”的题目，**贪心会失效**。

### 三、 经典算法演化路径全景复盘

既然贪心在多分支交织下会失效，我们来看看你的那条神级路径在这道题里是怎么走完闭环的：

```text
[ 1. 暴力 DFS / Backtracking ]
          │ (指数级爆搜，遇到重叠子问题当场超时 TLE)
          ▼
[ 2. 记忆化搜索 (Top-down DP / Cache) ]
          │ (加上 memo 备忘录，算过的子串直接返回，把树裁剪成有向无环图 DAG)
          ▼
[ 3. 动态规划 (Bottom-up DP) ]
          │ (从小到大递推：dp[i] = min(dp[i-1]+1, dp[j]))
          ▼
[ 4. 贪心 (Greedy) ] ──> ❌ 唯独这题不通！
```

- **为什么无法跨越到贪心？**
- 因为贪心要求问题必须具备“贪心选择性质”（即局部最优的选择可以直接推导出全局最优）。但本题由于词典的组合形态太诡异（短单词交错可能比长单词拼得更干净），局部选择无法保证全局，因此断在了 DP 这一层，无法进化成纯贪心。

### 💡 核心总结
老铁，你对算法演化路径的宏观直觉完全正确！在刷题时：
- 遇到求**方案数 / 最值**且存在**重叠子问题**时，大胆按照 `DFS ➔ 记忆化 ➔ DP` 的路线推演。
- 但同时要保持警惕：**并不是所有能用 DP 的题都能用贪心。** 只有当“每一步只做当下最优决定，且绝不后悔”被数学证明成立时，贪心大旗才能插上去！🔥

同样都是回溯（Backtracking），为什么 LeetCode 698（划分为 $k$ 个相等子集）加上剪枝能飞快跑过，而 LeetCode 2707（字符串中的额外字符）如果用纯回溯却会当场暴毙（TLE）？

关键在于两道题的“决策树形态”和“重叠子问题的恐怖程度”有本质区别。咱们从底层拆解一下原因：

### 1. 决策树的分支广度（$k$ 叉树 vs 字典长度树）
- **LeetCode 698 的回溯**：
  - 每一个数字只有 $k$ 个去处（尝试放入 $k$ 个桶中的某一个）。
  - 树的宽度是固定的 $k$（比如 $k = 4$ 或 $5$）。虽然是指数级，但由于剪枝极其凶残（大数开路、超标直接跳、空桶直接 `break`），合法的有效分支被压得非常少。
- **LeetCode 2707 的回溯**：
  - 每一个位置 `i` 面临的分支是什么？是去字典里匹配所有可能的前缀单词！
  - 如果你的词典很大，或者字符串里有很多局部匹配成功的分支，每一个状态可能衍生出好几个甚至十几个不同的单词跳转分支。树的扩散速度极快。

### 2. 致命痛点：“重叠子问题”的密度（最核心的原因）
纯回溯之所以恐怖，是因为它不知道自己走过重复的弯路。

咱们看看 2707 题中纯回溯会遇到多可怕的重复：
假设字符串 `s = "aaaaa..."`，词典里有 `["a", "aa", "aaa"]`。
- 你可以先选 `"a"`，再选 `"aa"`，最后到达索引 3。
- 你也可以先选 `"aa"`，再选 `"a"`，最后同样到达索引 3。
- 你甚至可以把前三个字符都当成额外字符跳过，最终还是到达索引 3。

在纯 Backtracking 下，计算机对“从索引 3 开始到结尾怎么切”这一段完全相同的子问题，会不厌其烦地、成千上万次地重复搜索！
因为字符串具有连续可切分的特性，后面产生相同状态的概率呈指数级爆炸。纯回溯没有备忘录（Cache）去记住 `dfs(3)` 的结果，导致大量算过的体力活被白白浪费。

### 3. 为什么 698 没这个问题，而 2707 必须上 DP？
- **698 拼的是“桶”**：每个数字只能用一次，数组长度 $N$ 通常很小（一般 $N \le 16$ ）。有限的元素和极强的数学剪枝（`sum % k != 0`、降序卡死）让它硬生生扛住了回溯。
- **2707 拼的是“字符串切分”**：字符串长度 $N$ 通常可以达到 $50$ 甚至更高。在长度为 50 的字符串面前，指数级的重叠子问题如果不加 DP 备忘录或迭代递推，计算量直接从地球干到宇宙边缘。

### 💡 终极对比
- **698 赢在“强剪枝”**：靠大数压顶和空桶拦截，把回溯树砍得稀碎，勉强用回溯过了。
- **2707 输在“重叠太密”**：路径交织太厉害，纯回溯会陷入无限的重复计算。所以它必须进化到 DP（用表格记住每个位置的最优解），把 $O(2^N)$ 的指数级爆搜直接降维打击成 $O(N^2)$ 的优雅递推！

虽然纯 DFS（回溯）在 LeetCode 2707 上会遇到上面提到的重叠子问题从而导致超时（TLE），但写出它的 DFS 版本能极其直观地帮我们理清从哪个位置开始切、怎么分叉、怎么拿返回值。

以下是 LeetCode 2707 的纯 DFS（回溯）Python3 工业级实现：

```python
from typing import List


class Solution:

  def minExtraChar(self, s: str, dictionary: List[str]) -> int:
    word_set = set(dictionary)
    n = len(s)

    # 定义 dfs(i)：从字符串索引 i 开始到末尾（s[i...]），切分所需的最少额外字符数
    def dfs(i: int) -> int:
      # 递归出口：如果已经扫描到字符串末尾，不需要额外字符
      if i == n:
        return 0

      # 策略 1：把当前字符 s[i] 当作额外字符直接放弃
      # 代价是 1，然后递归去处理下一个位置 i + 1
      min_extra = 1 + dfs(i + 1)

      # 策略 2：尝试以当前索引 i 作为起点，向后匹配所有可能长度的子串
      # 如果 s[i:j] 在词典里，说明这段不需要额外字符，直接“跳”到 j
      for j in range(i + 1, n + 1):
        sub = s[i:j]
        if sub in word_set:
          # 如果这段在词典中，后续的代价就是 dfs(j)，不需要额外增加代价
          min_extra = min(min_extra, dfs(j))

      return min_extra

    return dfs(0)
```

### 这段 DFS 的代码逻辑拆解：

1. **树的分支选择**：
   - **分支 1（跳过当前字符）**：`1 + dfs(i + 1)` —— 强行把当前字符扔掉，代价 +1，继续往后看。
   - **分支 2（字典单词匹配）**：通过内层 `for` 循环不断扩大截取范围 `s[i:j]`。只要发现它在 `word_set` 里，就直接把控制权交接给 `dfs(j)`。

2. **为什么会超时（TLE）**：
   - 比如 `s = "aaaaa..."`，你可以通过不同的组合路径多次落到同一个索引 `i` 上。纯 DFS 没有记忆功能，会把相同的 `dfs(i)` 重复计算无数次，导致指数级爆炸。
   - **平滑升级药方**：如果在 `def dfs(i)` 上方加上 `@functools.cache`（或者手写一个 `memo` 数组），它就瞬间变成了**记忆化搜索（Top-down DP）**，超时问题立刻迎刃而解！

## 继续加码!!!

如果我们在纯 DFS 的基础上加入 `@functools.cache`（或者手写 `memo` 字典），这段代码就会瞬间蜕变成**记忆化搜索（Top-down DP）**。

### 💻 加入 Cache 的完整 Python3 代码：

```python
import functools
from typing import List


class Solution:

  def minExtraChar(self, s: str, dictionary: List[str]) -> int:
    word_set = set(dictionary)
    n = len(s)

    # 加上 cache 装饰器，瞬间消除重复子问题！
    @functools.cache
    def dfs(i: int) -> int:
      if i == n:
        return 0

      # 策略 1：把当前字符当作额外字符
      min_extra = 1 + dfs(i + 1)

      # 策略 2：尝试匹配字典中的单词
      for j in range(i + 1, n + 1):
        if s[i:j] in word_set:
          min_extra = min(min_extra, dfs(j))

      return min_extra

    return dfs(0)
```

### 为什么加了 `@functools.cache` 就能直接起飞？

1. **把“爆炸树”裁剪成“有向无环图 (DAG)”**：
   - 纯 DFS 面对的是一棵宽度极宽、深度极深的指数级爆炸树。
   - 当加入 cache 后，一旦计算机算过某一个特定索引 `i`（比如 `dfs(3)`）的最优解，就会把结果存进内存大账本里。
   - 下一次别的路径又走到索引 `3` 时，计算机绝不会再往下盲目搜索，而是直接“秒查账本、光速返回”！

2. **时间与空间维度的降维打击**：
   - **时间复杂度**：从原本的恐怖指数级（$O(2^N)$ 或更高）直接降维打击到 $O(N^2 \cdot L)$（其中 $N$ 是字符串长度，$L$ 是单词最大长度）。
   - **空间复杂度**：由于备忘录最多存储 $N$ 个状态（`dfs(0)` 到 `dfs(N)`），递归栈深最大为 $N$，空间复杂度为 $O(N + M)$（$M$ 为字典的哈希集合开销）。

这就是从暴力回溯跃迁到记忆化搜索的极致魅力！🔥

---

### 工业级 DP 代码核心逻辑拆解：

1. **状态定义（State Definition）**：
   - `dp[i]` 明确锁定为：“前 `i` 个字符（即从下标 `0` 到 `i-1` 的子串）里，最少会丢掉几个额外字符”。
   - 我们的最终目标就是求出 `dp[n]`（整个字符串算完后的最优解）。

2. **状态转移方程的双重保障（State Transition）**：
   - **保底选择**：每次先看 `dp[i] = dp[i-1] + 1`，意思是“把当前字母当成废物丢掉，代价 +1，直接继承前一个位置的最优解”。
   - **优化选择**：内层用 `for j in range(i)` 回溯去查：如果截取出来的子串 `s[j:i]` 刚好在 `word_set` 里，说明这段大吉大利、无额外损耗，那么 `dp[i]` 就可以直接由更早的 `dp[j]` 平移白嫖过来：`dp[i] = min(dp[i], dp[j])`。

3. **时空复杂度核验（Complexity Verification）**：
   - **时间复杂度**：$O(N^2 \cdot L)$ —— 其中 $N$ 是字符串 `s` 的长度，$L$ 是单词的最大长度。两层循环共计约 $N^2$ 次状态转移，每次切片和哈希表查找最长耗时与单词长度 $L$ 相关。对于数据范围而言性能极佳。
   - **空间复杂度**：$O(N + M)$ —— 其中 $N$ 为 DP 数组的空间开销，$M$ 为哈希集合存储词典所有单词的内存开销。

---

确实，从理论的大 O 渐进复杂度来看，cache和DP的纯算法时间复杂度完全是一样的——都是 $O(N^2 \cdot L)$。

因为不管是自顶向下的“递归 + Cache”，还是自底向上的“迭代 DP”，它们本质上都在解同一张有向无环图（DAG）的状态转移网：总共约 $N$ 个状态，每个状态最多回溯 $N$ 次、每次切片匹配耗时 $L$。

### 💡 既然时间复杂度一样，为什么在工程实践和面试中，我们更偏爱迭代版 DP 呢？

虽然时间复杂度同阶，但在底层物理运行开销（Constant Factor）上，迭代 DP 拥有降维打击般的优势：

1. **彻底消除函数调用栈开销（Stack Overhead）**：
   - 记忆化搜索（Cache）底层依然是递归。递归意味着每一次深入 `dfs(i)` 都要在系统栈里压入栈帧（Stack Frame），保存返回地址、局部变量等。当字符串很长、递归深度很深时，系统栈的频繁调度会带来不小的内存和时间损耗，甚至极端情况下会触发 `RecursionError: maximum recursion depth exceeded`（爆栈）。
   - 迭代 DP 纯靠一个简单的 `for` 循环推进，完全没有函数调用的额外开销。

2. **内存局部性原理（Cache Locality）与硬件级优化**：
   - 迭代 DP 的状态是一个扁平的一维数组 `dp = [0] * (n + 1)`，它在内存里是连续存储的。
   - 这非常符合 CPU 的硬件直觉：连续的内存地址能够完美触发 CPU 缓存预读（Cache Line），访问速度极快。
   - 而递归的备忘录通常是哈希表或装饰器缓存，散落在内存的各个角落，会导致较多的 CPU 缓存未命中（Cache Miss）。

3. **状态拓扑的确定性**：
   - 迭代 DP 的计算顺序是从左到右硬性递推的（`1` 到 `n`），每一步依赖的子状态（如 `dp[j]`）在之前已经百分之百算好了，没有分支回溯的迷茫。

### 🎯 终极结论
- **从算法思想上看**：记忆化搜索和 DP 是亲兄弟，一个是 Top-down（顺藤摸瓜），一个是 Bottom-up（积水成渊），时间复杂度完全一样。
- **从工程落地上看**：如果在面试或者刷题时能直接写出干净利落的迭代 DP，不仅能拿满分，还能向面试官证明你对计算机底层内存和执行开销有深刻的洞察！🔥

## 但是为什么不可以再进一步,使用贪心算法呢?

咱们把刚才针对 **LeetCode 2707（字符串中的额外字符）** 总结的“为什么贪心会翻车”的核心逻辑，用最纯粹的 Markdown 重新推演一遍，让你一眼看穿贪心在这里失效的底层物理本质：

### 一、 结论先行：这道题能用贪心吗？

答案是：**不能盲目用“局部贪心”，但可以通过“全局贪心视角（DP 的本质）”来通关。**

如果在面试时，你想用传统的**纯贪心直觉**去解这道题（比如：“每走到一个地方，优先匹配字典里**最长的那个单词**，能匹配就立刻切下去”），**你会当场被测试用例无情打脸。**

### 二、 为什么“最长匹配贪心”会翻车？（反例剖析）

假设：
- 字符串 `s = "catsanddog"`
- 字典 `dictionary = ["cat", "cats", "sand", "dog"]`

#### 🏃‍♂️ 纯贪心（每一步贪图眼前最大长度）的走法：
1. 从下标 `0` 开始看，能匹配的最长单词是什么？是 `"cats"`（长度 4）。
2. 贪心算法大喜：“好！选最长的 `"cats"`！” ➔ 剩下的字符串变成了 `"anddog"`。
3. 从下标 `4`（即 `"a"`）开始看，剩下字符串 `"anddog"`，能匹配的最长单词是 `"dog"`（在末尾），把中间的 `"and"` 全都当成额外字符丢掉。
4. **贪心算出来的额外字符数**：中间浪费了 `"and"`（3个字符）。

#### 💡 真实的全局最优解：
1. 先选 `"cat"`（长度 3） ➔ 剩下 `"sanddog"`。
2. 再选 `"sand"`（长度 4） ➔ 剩下 `"dog"`。
3. 最后选 `"dog"`（长度 3）。
4. **全局最优的额外字符数**：**`0` 个额外字符！**

#### ❌ 贪心翻车的原因：
**局部的“最长匹配”并不代表全局的“额外字符最少”。** 贪心由于“目光短浅”（只看眼前能吃多大一块），常常会把后面更完美、能凑出无缝拼接的宝贵前缀给提前霍霍掉。这就是为什么这类求“全局最优化/最少代价”的题目，**贪心会失效**。

### 三、 为什么无法跨越到贪心？

- 贪心要求问题必须具备**“贪心选择性质”**（即局部最优的选择可以直接推导出全局最优）。
- 但本题由于词典的组合形态太诡异（短单词交错可能比长单词拼得更干净），局部选择无法保证全局，因此断在了 DP 这一层，无法进化成纯贪心。
