# 1095. 山脉数组中查找目标值 - 题目解析与答案

## 一、 题目描述

给定一个山脉数组 `mountainArr`，返回最小的 `index` 使得 `mountainArr.get(index) == target`。如果不存在这样的 `index`，返回 `-1`。

**什么是山脉数组？**
* 数组长度 $\ge 3$。
* 在算法中，索引 $i$ 满足 $0 < i < \text{length} - 1$ 的限制条件。
  * $arr[0] < arr[1] < \dots < arr[i]$
  * $arr[i] > arr[i + 1] > \dots > arr[\text{length} - 1]$

**限制条件：**
* 你无法直接访问山脉数组，只能通过 `MountainArray` 接口：
  * `MountainArray.get(k)`：返回数组中下标为 $k$ 的元素。
  * `MountainArray.length()`：返回数组的长度。
* 调用 `MountainArray.get` 超过 $100$ 次的提交会被判定为错误答案。

## 二、 解题思路

由于题目限制了 `get` 的调用次数不能超过 $100$ 次，且数组具有单调性（先升后降），我们可以很自然地联想到 **二分查找**。

整个解题过程可以分为以下 **三个步骤**：
1. **寻找峰顶元素**：利用二分查找找到山脉数组的最高点（峰顶）索引 $peakIndex$。
2. **在左侧升序数组中查找**：在 $[0, peakIndex]$ 区间内进行升序二分查找。如果找到 `target`，直接返回对应的索引。
3. **在右侧降序数组中查找**：如果在左侧没有找到，则在 $[peakIndex + 1, \text{length} - 1]$ 区间内进行降序二分查找。如果找到，返回索引；若仍未找到，返回 `-1`。

## 三、 Python 代码实现

```python
# """
# This is MountainArray's API interface.
# You should not implement it, or speculate about its implementation
# """
#class MountainArray(object):
#    def get(self, index):
#        """
#        :type index: int
#        :rtype int
#        """
#
#    def length(self):
#        """
#        :rtype int
# """
class Solution:
    def findInMountainArray(self, target: int, mountainArr: 'MountainArray') -> int:
        n = mountainArr.length()
        
        # 步骤 1：使用二分查找找到峰顶元素的索引
        left, right = 0, n - 1
        while left < right:
            mid = (left + right) // 2
            if mountainArr.get(mid) < mountainArr.get(mid + 1):
                left = mid + 1
            else:
                right = mid
        peak = left
        
        # 步骤 2：在左半部分（升序）进行二分查找
        left, right = 0, peak
        while left <= right:
            mid = (left + right) // 2
            val = mountainArr.get(mid)
            if val == target:
                return mid
            elif val < target:
                left = mid + 1
            else:
                right = mid - 1
                
        # 步骤 3：在右半部分（降序）进行二分查找
        left, right = peak + 1, n - 1
        while left <= right:
            mid = (left + right) // 2
            val = mountainArr.get(mid)
            if val == target:
                return mid
            elif val < target:
                right = mid - 1  # 降序数组中，值变小说明目标在左边（索引更小的方向）
            else:
                left = mid + 1   # 值变大说明目标在右边（索引更大的方向）
                
        return -1
```

## 四、 复杂度分析

* **时间复杂度**：$O(\log N)$。其中 $N$ 是数组的长度。寻找峰顶需要 $O(\log N)$，左右两部分二分查找最多各需要 $O(\log N)$，总共的接口调用次数远小于 $100$ 次（在 $N \le 10^4$ 的情况下，调用次数通常在 $30$ 次左右），完全满足题目限制。
* **空间复杂度**：$O(1)$。只需要常数级别的额外空间来存储指针变量。

## 🗺️ 解法思路大盘点：从笨办法到绝顶聪明

### 💡 思路一：暴力平推流（Linear Scan / 顺藤摸瓜）
* **怎么想的**：既然管理员说山有那么多格子，那我不动脑子，直接从头（第 0 个）开始，一个一个格子问管理员：“是你吗？不是。那下一个是你吗？”一直摸到头。
* **致命痛点**：
  * **时间复杂度**：$\mathcal{O}(N)$。如果山长 10 万个格子，你最多得问 10 万次。
  * **超次数嫌疑**：管理员有严格的查询限制（不能超过 100 次）。这种暴力平推流在面对 LeetCode 的大规模测试用例时，直接就会被评测机无情地按死在超时（Time Limit Exceeded）的沙滩上。

### 🚀 思路二：三段式二分查找（The Standard Optimal Approach ➔ 正统最优解）
* **怎么想的**：也就是咱们刚刚盘明白的那个逻辑——分而治之。
  * **第 1 次二分**：用二分法找出山顶在哪。
  * **第 2 次二分**：在左边那段“上坡路”（升序区间）里用二分找目标值。
  * **第 3 次二分**：如果在左边没找到，转到右边那段“下坡路”（降序区间）里用二分找。
* **为什么它是工业级最优**：
  * **时间复杂度**：$\mathcal{O}(\log N)$。因为每一次二分都是“对半砍”，哪怕数组长度有 10 亿，总共也只需要问十几次到几十次，绝对不会超过 100 次的上限！
  * **空间复杂度**：$\mathcal{O}(1)$。只用了几个指针变量，没有额外开辟任何大数组。

# 你可能纳闷：“怎么在第一步找山顶时，用的是 left < right（没有等于号），而到了第二步和第三步在左右两边找宝藏时，突然又变成 left <= right（带等于号）了呢？”

咱们别被代码吓住，用大白话和最直观的物理逻辑把它们彻底理清：

🏔️ 第一步：找山顶为什么用 left < right？
我们的目标：我们要通过二分“缩小包围圈”，最后把唯一的那个最高峰死死夹在中间，直到 left 和 right 撞到同一个格子上（即 left == right），循环就结束，这唯一的落脚点就是山顶。

为什么不用等于号：因为如果写了 left <= right，当 left 和 right 相遇时，里面还会再算一次 mid，这在寻找“单峰边界”时容易导致死循环或者指针越界。所以找山顶的经典模板就是 while left < right:，最后靠 left 或 right 停在顶峰收工。

🔍 第二、三步：在左边/右边找宝藏为什么又用 left <= right？
我们的目标：这时候我们的任务变了！我们不是找边界，而是要在一段明确的区间里（比如左边上坡路 [0, peak]）挨个排查每一个格子，看看里面究竟有没有藏着我们要找的 target。

为什么必须带等于号 (left <= right)：

想象一下，如果数组里只有 1 个格子（比如 left = 0, right = 0），如果你的循环条件写的是 left < right，因为 0 < 0 不成立，这个唯一的格子连看一眼的机会都没有，直接就被循环漏掉了！

如果 target 刚好就藏在这个唯一的格子里，程序就会直接漏看并返回 -1。

所以，只要是“在一个确定的区间里精确查找某个具体数值（Target Search）”，就必须用带等于号的标准闭区间二分模板 while left <= right:，确保每一个格子（包括 left == right 时那最后一个重合的格子）都被检查到。

💡 一句话总结两者的本质区别：
找山顶：是“区间收缩法”（寻找一个边界极值），不需要检查最后一个重合点是否满足条件，用 left < right。

找宝藏：是“精确命中法”（在已知区间内捞具体数字），必须把每一个角落（包括单元素区间）都搜干净，用 left <= right。

既然找山顶时循环条件是 `left < right`（没有等于号），那如果 `left` 和 `right` 相遇了（也就是等于了），为什么循环就直接停了？如果它俩相等时刚好卡在山顶，不等它俩相等怎么行？

咱们用最纯粹的物理直觉，把为什么“不能写等于号、写了会发生什么”彻底看透：

### 🏔️ 核心物理真相：`left` 和 `right` 从来不是“去寻找山顶”，而是“把山顶夹在中间”！

在写第一步二分时，我们的逻辑是：
```python
left, right = 0, n - 1
while left < right:
    mid = (left + right) // 2
    if mountainArr.get(mid) < mountainArr.get(mid + 1):
        left = mid + 1  # 还在上坡，山顶在右边
    else:
        right = mid     # 在下坡，山顶在左边或就是当前位置

```

请注意看这里指针的流向：

* 当触发 `left = mid + 1` 时，`left` 主动放弃了当前位置，往右跨了一步。
* 当触发 `right = mid` 时，`right` 收缩到了 `mid`。

这意味着什么？
👉 **山顶永远被死死地夹在当前的 `left` 和 `right` 这两个边界之间！**


### ⚠️ 如果你脑子一热，写成了 `while left <= right:` 会发生什么灾难？

假设当某一次循环时，`left` 和 `right` 终于靠拢了，它们刚好同时指向了真正的山顶（即 `left == right == peak`）。

如果你用了带等于号的 `while left <= right:`，程序会怎么执行：

1. 它会算出 `mid = (left + right) // 2`，此时 `mid` 依然指向山顶。
2. 接下来，它会去查 `mountainArr.get(mid)` 和 `mountainArr.get(mid + 1)`。
3. **致命的问题来了**：`mid` 已经是山顶了，那 `mid + 1` 就在山顶的右边（下坡路）！
4. 所以，山顶的值一定会比右边的值大（`get(mid) > get(mid + 1)`）。
5. 按照我们的 `else` 逻辑，它会执行：`right = mid`。
6. **无限死循环爆发**：此时 `left` 没动（依然在山顶），`right` 被赋值成了 `mid`（也就是山顶）。下一轮循环开始，`left` 和 `right` 还是相等，继续算 `mid`，继续执行 `right = mid`……代码直接卡死在原地，CPU 烧毁！

### 💡 总结一句话：为什么找山顶不能用等于号？

* 因为在找山顶时，我们的 `right = mid` 把包含山顶的可能落脚点死死保留了。
* 当 `left` 和 `right` 终于在某个点撞在一起（`left == right`）时，这个点就是山顶，不需要再进行任何多余的探测了。
* 如果你写了 `left <= right`，当它们在山顶相遇时，代码还要硬着头皮再往下算一次 `mid + 1`（去跟下坡比），从而引发灾难性的死循环。

所以，找山顶的 `while left < right:` 就像是两个围捕的警察，当他俩在顶峰面对面撞个正着时，目标就已经落网，直接收网即可！

# Question: 为什么二分查找让人发狂？一文彻底搞懂 mid、mid - 1 与边界收缩的物理本质

每一个刷到 LeetCode 1095（山脉数组）或者二分查找变体的人，都会在 `right = mid` 和 `right = mid - 1`、`left < right` 和 `left <= right` 的死胡同里绕到怀疑人生。

你觉得“好乱”，是因为你之前可能在死记硬背别人的代码模版。今天咱们直接把二分查找的**底层物理本质**给它掀开，让你一眼看穿：**什么时候该用 `mid`，什么时候该用 `mid - 1`！**

## 💡 一、 核心真相：`mid` 还是 `mid - 1` 取决于“你当前的 `mid` 还能不能要？”

在二分查找的世界里，所有的混乱都来自于**边界的缩圈逻辑**。记住一句话：

> **`mid` 已经被你探测过了。如果经过对比，你确定当前的 `mid` 绝对不可能是你要找的答案，那么就可以放心地把它踢出去，写 `mid - 1` 或 `mid + 1`；**
> **但如果当前的 `mid` 有可能是你要找的答案（或者它还有用），你就绝对不能一脚把它踢开，只能写 `mid`！**

咱们用 LeetCode 1095 寻找山顶（Peak）的场景来做个终极对比：

## ⛰️ 二、 为什么标准找山顶必须写 `while left < right` 且 `right = mid`？

在寻找山顶时，我们的核心判断逻辑是：`mountainArr.get(mid) < mountainArr.get(mid + 1)`
这意味着：**当前 `mid` 的右边比它大，说明 `mid` 在上坡阶段，它绝对不可能是山顶！山顶在它的右边。**

### 1. 为什么不能写 `right = mid - 1`？
- 既然 `mid` 比 `mid + 1` 小，那 `mid` 肯定不是山顶。但 `mid + 1` 有没有可能是山顶？有可能是！
- 如果你手一抖写了 `right = mid - 1`，你就把 `mid` 连同它的右边一起粗暴地砍掉了，万一 `mid + 1` 就是全场最高峰，你就直接把答案**亲手弄丢了**！
- 所以，你只能让 `left = mid + 1`（因为 `mid` 肯定不是，主动放弃它），而把 `right` 保留在 `mid` 的位置。**为什么是 `right = mid` 而不是 `mid - 1`？** 因为万一当前的 `mid` 刚好就是最高峰呢？你如果写了 `right = mid - 1`，就把当前的峰顶给漏掉了！所以必须把 `right` 保留在 `mid` 的位置，等待下一步紧缩。

### 2. 为什么配合 `right = mid` 必须用 `while left < right`（不带等于号）？
- 想象一下，当 `left` 和 `right` 慢慢靠拢，最后只差格子时（比如 `left = 4, right = 5`，`mid = 4`）。
- 如果 `arr[4] > arr[5]`，触发了 `right = mid`，即 `right = 4`。
- 此时 `left = 4, right = 4`。如果你写的是 `while left <= right`，下一轮循环里 `mid` 还是 4，它又去跟 5 比，就会陷入**死循环（CPU 烧毁）**！
- 所以，当 `right = mid` 时，区间是向左包容的，必须用 `left < right`。当它们俩撞在一起时，那个重合点刚好就是山顶，直接收网！

## 🔍 三、 什么时候可以安心写 `right = mid - 1`？

只有在一种情况下，你才可以理直气壮地写 `right = mid - 1`：
👉 **当你要找的是一个“确定的目标值（比如 Target）”，并且你通过比对发现 `arr[mid]` 比目标值还要大，说明 `mid` 绝对不可能是目标，且目标一定在它的左边。**

比如标准的升序二分查找：

```python
while left <= right:
    mid = (left + right) // 2
    if arr[mid] == target:
        return mid
    elif arr[mid] > target:
        right = mid - 1  # 💡 既然 arr[mid] 已经比 target 大了，当前的 mid 绝对多余，直接 -1 踢出局！
    else:
        left = mid + 1   # 💡 既然 arr[mid] 比 target 小，当前的 mid 绝对不可能是，直接 +1 踢出局！
```

为什么这里可以用 `<=` 且可以用 `mid - 1`？
因为每一次 `mid` 被比对过后，如果它不是 target，它就没有任何利用价值了，我们通过 `mid + 1` 和 `mid - 1` 把它彻底排挤出搜索圈。

## 📋 四、 终极避坑口诀（建议截图保存）

### 1. 寻找“某种极值边界 / 峰值 / 边界条件”（如 LeetCode 1095 找山顶、或者找左/右边界）
- **逻辑**：当前 `mid` 可能是答案，也可能不是，但不能盲目丢弃。
- **动作**：用 `while left < right`，配合 `right = mid` 或 `left = mid + 1`。

### 2. 在有序数组中精确寻找一个具体的 `target` 值
- **逻辑**：当前 `mid` 如果不等于 target，它就毫无用处，两边可以随便切。
- **动作**：用 `while left <= right`，配合 `right = mid - 1` 和 `left = mid + 1`。

> 💡 **老铁核心心法**：
> 把这个逻辑在脑子里过一遍：**“留着有用就写 `mid`，确认无用就写 `mid - 1`”**。

# LeetCode 26. Remove Duplicates from Sorted Array (删除有序数组中的重复项)

## 📝 1. 题目描述 (Description)
给你一个非严格递增排列的数组 `nums`，请你**原地**删除重复出现的元素，使每个元素只出现一次，返回删除后数组的新长度。元素的相对顺序应该保持一致。然后返回 `nums` 中唯一元素的个数。

## 💡 2. 核心直觉与解题范式 (Core Intuition)
这道题是经典的**双指针流（快慢指针 / Slow-Fast Pointers）**：
1. **慢指针 `slow`**：负责圈定“无重复合法序列”的右边界。
2. **快指针 `fast`**：负责像侦察兵一样从头到尾扫荡整个数组。
3. **物理动作**：
   - 如果 `nums[fast] != nums[slow]`，说明发现了一个全新的不同数字！
   - 此时我们先把 `slow` 往前挪一步（`slow += 1`），然后把 `nums[fast]` 赋给新的 `slow` 位置（`nums[slow] = nums[fast]`）。
   - 遍历结束后，合法无重复元素的总长度就是 `slow + 1`。

## 💻 3. Python3 完美通关代码 (Solution)

```python
class Solution(object):
    def removeDuplicates(self, nums):
        """:type nums: List[int]

        :rtype: int
        """
        if not nums:
            return 0

        slow = 0
        for fast in range(1, len(nums)):
            if nums[fast] != nums[slow]:
                slow += 1
                nums[slow] = nums[fast]

        return slow + 1
```

## ⏱️ 4. 复杂度分析 (Complexity Analysis)

- **时间复杂度**：O(N)
  - 快指针 `fast` 对整个数组进行了一次线性扫描，每个元素仅被访问一次。
- **空间复杂度**：O(1)
  - 纯原地修改数组，没有额外开辟任何辅助的数据结构或存储空间。

class Solution(object):

# LeetCode 19. 删除链表的倒数第 N 个结点 (Remove Nth Node From End of List)

## 🎯 一、 核心考点与物理直觉

- **题目大意**：给你一个单链表的头节点 `head`，请你删除链表的倒数第 `n` 个节点，并且返回链表的头节点。
- **物理直觉**：
  - 单向链表的天然劣势在于：我们**只能从前往后走**，没法提前知道链表的总长度是多少，也无法直接倒着数。
  - 如果用暴力解法，我们需要先遍历一遍统计总长度 $L$，然后再走 $L - n$ 步去执行删除。这样需要遍历两次。
  - **大厂面试官想看的降维打击流——“双指针时间差错位法”**：
    - 我们让 **快指针（Fast）** 先向前走 $n$ 步。
    - 此时，**慢指针（Slow）** 和快指针之间就拉开了一个固定的距离差（$n$ 步）。
    - 接着，快慢指针以相同的速度**同时向后走**。当快指针顺利到达终点（`None`）时，慢指针刚好停在**被删除目标节点的前一个位置**！
    - 配合我们链表必备的 **虚拟头节点（Dummy Head）**，可以直接无脑安全地摘除目标节点，完美做到**只遍历一次**！

## 🛠️ 二、 解题三步走框架

1. **安插哨兵（Dummy Head）**：
   - 为什么要加 `dummy`？因为如果链表只有一个节点，我们要删除倒数第 1 个节点（即头节点本身），如果没有 `dummy`，删除头节点的逻辑会变得非常繁琐。加上 `dummy = ListNode(0, head)` 后，任何节点（包括头节点）都有前驱节点。
2. **拉开时间差（Fast 先走 $n$ 步）**：
   - 让 `fast` 指针从 `dummy` 出发，先走 $n$ 步。
3. **齐头并进与精准摘除**：
   - `slow` 从 `dummy` 出发，`fast` 和 `slow` 同时向后移动，直到 `fast.next` 为空（即 `fast` 走到最后一个节点）。
   - 此时 `slow.next` 就是我们要删掉的倒数第 $n$ 个节点。执行 `slow.next = slow.next.next` 即可完成精准爆破。

## 💻 三、 Python3 完美通关代码 (Solution)

```python
# Definition for singly-linked list.
# class ListNode(object):
#     def __init__(self, val=0, next=None):
#         self.val = val
#         self.next = next

class Solution(object):
    def removeNthFromEnd(self, head, n):
        """:type head: Optional[ListNode]
        :type n: int
        :rtype: Optional[ListNode]
        """
        # 1. 建立虚拟头节点，防范边界崩溃
        dummy = ListNode(0, head)
        slow = dummy
        fast = dummy
        
        # 2. 让快指针先向前走 n 步
        for _ in range(n):
            fast = fast.next
            
        # 3. 快慢指针同时前进，直到 fast 到达链表末尾
        while fast and fast.next:
            slow = slow.next
            fast = fast.next
            
        # 4. 跨过被删除的节点
        slow.next = slow.next.next
        
        # 5. 返回真正的头节点
        return dummy.next
```

## 📊 四、 复杂度核验 (Complexity Analysis)

- **时间复杂度**：$\mathcal{O}(L)$
  - 其中 $L$ 是链表的长度。快指针先走 $n$ 步，随后快慢指针一起走完剩下的 $L - n$ 步，总共遍历的节点数恰好是线性级别，只需一遍扫描！
- **空间复杂度**：$\mathcal{O}(1)$
  - 只需要常数级别的几个指针变量（`dummy`, `slow`, `fast`），没有开辟任何额外的存储空间，空间利用率拉满！

 
# 链表算法核心心法：什么时候从 dummy 开始？什么时候从 head 开始？

在链表算法题中，很多同学最容易翻车、最感迷茫的一点就是：“我到底该让指针从 `dummy`（虚拟头节点）出发，还是直接从 `head`（真实头节点）出发？”

掌握这个边界问题的关键，只需记住一个绝对铁律：
> **判断的唯一标准，在于“你是否需要对头节点（head）本身进行修改、删除、或者在它前面拼新节点”！**


## 🛡️ 一、 什么时候必须从 `dummy` 开始？

**【核心场景】**：当**头节点（head）本身可能会被改变、被删除、或者需要在头部前面加新节点**时，必须毫不犹豫地使用 `dummy`（虚拟头节点）！

因为单链表是**单向**的。如果你直接让指针从 `head` 出发，一旦你想把 `head` 删掉，或者在 `head` 前面插入一个新节点，那么原本的“头指针”就会指向错误的位置或者变成空，导致你最后无法正确返回整条链表。

### 1. 经典代表 1：LeetCode 19. 删除链表的倒数第 N 个结点
- **为什么从 `dummy` 开始？**
  - 如果链表只有一个节点（比如 `[1]`），我们要删倒数第 1 个节点。
  - 如果不用 `dummy`，直接从 `head` 开始找，删完之后链表就变成空了，`head` 变成了 `None`。这时候代码极容易因为边界处理不当而报错。
  - **用了 `dummy` 之后**：`dummy = ListNode(0, head)`。让 `slow` 和 `fast` 从 `dummy` 出发。这样即便删的是真正的头节点 `head`，`dummy.next` 也能完美、安全地指向被更新后崭新的头节点！

### 2. 经典代表 2：LeetCode 203. 移除链表元素（删除所有值为 val 的节点）
- **为什么从 `dummy` 开始？**
  - 如果原链表是 `[1, 2, 6]`，要删除值为 `6` 的节点，那很简单。
  - 但如果原链表是 `[6, 1, 2, 6]`，**第一个节点（head）本身就是需要被删除的目标**！
  - 如果不设 `dummy`，你的 `head` 会被直接跳过，但你的函数返回值（返回新的头节点）就会乱套。有了 `dummy = ListNode(0, head)` 后，不管删多少个开头的 `6`，`dummy.next` 永远稳稳地指向最终活下来的那个真实头节点。

### 3. 经典代表 3：LeetCode 2. 两数相加 / LeetCode 21. 合并两个有序链表
- **为什么从 `dummy` 开始？**
  - 这类题目属于**“凭空造新链表”**。
  - 一开始我们手里只有一个空的返回壳子，我们需要一个哨兵 `dummy` 站在最前面当锚点，后面用一个 `curr` 指针不断往 `dummy` 后面接新节点。最后直接返回 `dummy.next` 即可。


## 🚀 二、 什么时候直接从 `head`（或 `head` 派生的指针）开始？

**【核心场景】**：当**头节点（head）绝对不可能被删除或改变，你仅仅是需要去“遍历”、“查找中点”、“只读观察”或者“局部反转”**时，直接从 `head` 开始即可！

### 1. 经典代表 1：LeetCode 876. 链表的中间结点 / LeetCode 141. 环形链表
- **为什么从 `head` 开始？**
  - 我们只是要找中点，或者检测有没有环。
  - 原链表的结构和头节点**完全不需要被修改**，也没有人会被删除。
  - 所以直接 `slow, fast = head, head`，让它们在原地开始跑就行了。

### 2. 经典代表 2：LeetCode 143. 重排链表
- **为什么找中点时从 `head` 开始？**
  - 寻找中点的快慢指针 `slow, fast = head, head` 是直接从头开始跑的。
  - 至于后面的“断开、反转、合并”，虽然改变了链表的指针指向，但**整条链表的真正大头 `head` 始终安然无恙地排在最前面**，不需要用 dummy 去保护头部。

### 3. 经典代表 3：LeetCode 206. 反转链表
- **为什么直接操作？**
  - `prev = None`, `curr = head`。
  - 虽然它改变了所有节点的指向，但因为我们最后是要返回翻转后的新头节点（也就是原来的尾节点，即代码里的 `prev`），所以从 `head` 直接开干完全没有问题。


## 💡 三、 终极口诀总结

下回在考场上写链表题时，动手前先问自己一句话：
> **“我这一波操作，会不会把原本的第一个节点（head）给删了、或者给挤到后面去变成第2个、第3个节点？”**

- **会（或者不确定）** ➔ **立刻上 `dummy = ListNode(0, head)`，所有指针从 `dummy` 出发！**
- **不会（只是只读遍历、找中点、或者在后面折腾）** ➔ **直接从 `head` 出发！**
