# 35. Search Insert Position (搜索插入位置)
Easy

## 📝 Description
Given a sorted array of distinct integers and a target value, return the index if the target is found. If not, return the index where it would be if it were inserted in order.

You must write an algorithm with $O(\log n)$ runtime complexity.

## 💡 Example 1:
* **Input:** `nums = [1,3,5,6]`, `target = 5`
* **Output:** `2`

## 💡 Example 2:
* **Input:** `nums = [1,3,5,6]`, `target = 2`
* **Output:** `1`

```python
class Solution(object):
    def searchInsert(self, nums, target):
        """
        :type nums: List[int]
        :type target: int
        :rtype: int
        """
        left, right = 0, len(nums) - 1
        
        while left <= right:
            mid = left + (right - left) // 2
            
            if nums[mid] == target:
                return mid
            elif nums[mid] < target:
                left = mid + 1      # 目标在右边，左指针右移
            else:
                right = mid - 1     # 目标在左边，右指针左移
                
        # 💡 为什么最后返回 left？
        return left
```

## 🔍 深度解析：为什么最后必须 `return left`？

这道题是二分查找最经典的“边界查找”变体。很多人疑惑为什么找不到时要返回 `left`，其实它是二分查找的一个物理必然结果：

### 1. 二分结束时的交错状态
当 `while left <= right:` 循环正常退出时，意味着 `left` 已经**大于** `right` 了（即 `left = right + 1`）。此时，两个指针形成了一种“大军合围”后的交叉状态。

### 2. `left` 停下的物理位置
* 在整个夹逼过程中，如果没找到 `target`，`right` 会一直往左收缩，`left` 会一直往右挺进。
* 当循环结束的那一瞬间，**`left` 刚好精准停在了“第一个大于 target 的元素”的位置上**。
* 如果 `target` 比数组里所有数都大，`left` 会一路向右跨过所有格子，最终停在 `len(nums)`（即数组的最末尾）。

### 3. 完美契合插入定义
这个刚好比 `target` 大的位置，或者说大军合围交错后的分界点，就是 `target` 按顺序理应插入的正确下标。所以最后无脑 `return left`，就能优雅通关。

### 📊 复杂度核验 (Complexity Analysis)
时间复杂度：O(log n)。二分查找每次将搜索空间对半砍，效率呈指数级上升。
空间复杂度：O(1)。只用了常数个指针变量（left, right, mid），没有占用额外的动态内存。

# LeetCode 355. Design Twitter (设计推特)

Medium Topics Companies

## 📝 1. 题目描述 (Description)
设计一个简化版的推特(Twitter)，可以让用户实现发送推文、关注/取消关注其他用户、以及获取自己及关注的人最近 10 条推文的 Feed 流（News Feed）。

实现 `Twitter` 类：
* `Twitter()` 初始化简易推特对象。
* `void postTweet(int userId, int tweetId)` 使用给定的 `userId` 和 `tweetId` 创建一条新推文。每次调用此函数都会使用一个唯一的 `tweetId`。
* `List<Integer> getNewsFeed(int userId)` 检索当前用户新闻 Feed 流中最近的 10 条推文 ID。新闻 Feed 流中的每一项都必须是由用户关注的人或者是用户自己发布的推文。推文必须 **按照时间倒序排序**（从最近到最旧）。
* `void follow(int followerId, int followeeId)` ID 为 `followerId` 的用户开始关注 ID 为 `followeeId` 的用户。
* `void unfollow(int followerId, int followeeId)` ID 为 `followerId` 的用户开始取消关注 ID 为 `followeeId` 的用户。

## 💡 2. 核心设计与物理直觉 (Core Design & Intuition)

这是一道极其经典的 **面向对象设计 (OOD) + 哈希表 + 堆 (Min-Heap / 优先队列)** 的系统设计题。核心难点在于 `getNewsFeed`：
1. **全局时间戳 (Timestamp)**：
   - 推文必须按时间倒序排列。我们需要一个全局自增的计数器 `self.time`，每次发推文时把当前时间戳打在推文上，保证时序严格一致。
2. **关系网维护 (Following List)**：
   - 用一个哈希表 `self.following = collections.defaultdict(set)` 来记录每个用户关注了哪些人。
   - **注意点**：用户默认是“关注自己的”（`userId` 必须在自己的关注列表里），这样获取 Feed 流时才能顺便把自己的推文捞出来。
3. **Feed 流聚合与多路归并 (K-Way Merge via Min-Heap)**：
   - 获取某个用户及其所有关注者的最近推文时，如果把所有人的推文无脑拿出来排序，效率会很低。
   - 最佳实践是：利用 **小顶堆 (Min-Heap)** 维护最多 10 个最新的推文，或者将多人的推文链表进行多路归并，高效选出时间最近的 10 条推文！

## 💻 3. Python3 完美通关代码 (Solution)

```python
import collections
import heapq

class Twitter(object):

    def __init__(self):
        # 全局时间戳，每发一条推文自增一次
        self.time = 0
        # 映射表：userId -> list of [time, tweetId]，存储每个用户发的推文
        self.tweets = collections.defaultdict(list)
        # 关系网：userId -> set of followeeId，存储每个用户关注的人
        self.following = collections.defaultdict(set)

    def postTweet(self, userId, tweetId):
        """:type userId: int
        :type tweetId: int
        :rtype: None
        """
        self.tweets[userId].append((self.time, tweetId))
        self.time += 1

    def getNewsFeed(self, userId):
        """:type userId: int
        :rtype: List[int]
        """
        res = []
        # 小顶堆，用来维护按时间最新的推文（堆顶存放最旧的，方便控制大小在 10 以内）
        min_heap = []
        
        # 用户自己也算自己的“关注对象”，必须把自己的 ID 加进去一起聚合
        self.following[userId].add(userId)
        
        # 遍历自己以及所有关注的人
        for followeeId in self.following[userId]:
            if followeeId in self.tweets:
                # 拿到该用户发的所有推文
                user_tweets = self.tweets[followeeId]
                # 从该用户最近的推文开始往前看
                for t, tweetId in reversed(user_tweets):
                    heapq.heappush(min_heap, (t, tweetId))
                    # 如果堆的大小超过了 10，把时间最旧的（堆顶）弹出，保持堆大小最多为 10
                    if len(min_heap) > 10:
                        heapq.heappop(min_heap)
                        
        # 弹出堆中所有元素，由于是小顶堆，我们需要按时间从大到小（倒序）排列结果
        while min_heap:
            t, tweetId = heapq.heappop(min_heap)
            res.append(tweetId)
            
        # 因为是从小到大弹出的，最后需要反转，让最近的推文排在最前面
        return res[::-1]

    def follow(self, followerId, followeeId):
        """:type followerId: int
        :type followeeId: int
        :rtype: None
        """
        self.following[followerId].add(followeeId)

    def unfollow(self, followerId, followeeId):
        """:type followerId: int
        :type followeeId: int
        :rtype: None
        """
        # 自己不能取消关注自己
        if followerId != followeeId and followeeId in self.following[followerId]:
            self.following[followerId].remove(followeeId)
```

### 复杂度核验 (Complexity Analysis)

#### 时间复杂度
* **postTweet**: $O(1)$，直接追加到列表中。
* **getNewsFeed**: $O(K \log U)$，其中 $U$ 是用户关注的人数，每次合并推文从 $U$ 个列表中取最值，$K$ 是要获取的条数（通常为 10）。
* **follow/unfollow**: $O(1)$，哈希表操作。

#### 空间复杂度
* **总体**: $O(T + U^2)$
* **说明**: 其中 $T$ 为推文总数，$U$ 为用户总数。主要用于存储所有人的推文历史和关注关系表。

### 空间复杂度分析：O(T + U^2)

空间复杂度的构成主要分为两部分：**推文存储**与**关注关系存储**。

#### 1. 推文存储空间：$O(T)$
* **含义**：$T$ 是系统内所有用户发布的推文总数。
* **原因**：无论用户如何关注或取关，系统都需要持久化保存每一条已发布的推文。每一条推文（包括 `tweetId` 和时间戳）都必须存储在内存中，因此这部分空间与推文总数呈线性关系。

#### 2. 关注关系存储空间：$O(U^2)$
* **含义**：$U$ 是系统中的用户总数。
* **原因**：这是基于“最坏情况”的假设：
    * 每一个用户都可以关注其他所有用户。
    * 如果系统中共有 $U$ 个用户，每个用户维护一个 `HashSet`（或类似结构）来记录他所关注的人。
    * 在极端情况下（例如社交网络是完全图），每个用户都关注了除了自己以外的 $U-1$ 个人。
    * 因此，总的关注关系边数为 $U \times (U - 1)$，即空间复杂度为 $O(U^2)$。

**总结**：
总空间复杂度 $O(T + U^2)$ 意味着系统不仅要为**海量推文内容**（$T$）付费，还要为**稠密的社交网络关系**（$U^2$）付费。在实际生产环境中，由于关注关系通常是稀疏的（远小于 $U^2$），实际的空间开销往往会更小。

# LeetCode 1834. 单线程 CPU (Single-Threaded CPU)

## 题目描述

给你一个二维数组 `tasks`，用于表示 $n$ 个任务，其中 $\text{tasks}[i] = [\text{enqueueTime}_i, \text{processingTime}_i]$：
* $\text{enqueueTime}_i$ 是第 $i$ 个任务被放入任务队列的时间。
* $\text{processingTime}_i$ 是执行第 $i$ 个任务需要花费的时间。

一个单线程 CPU 会按照以下策略运行任务：
1. 如果 CPU 空闲且没有任务可执行，CPU 保持空闲。
2. 如果 CPU 空闲但有可执行任务，CPU 会选择 **执行时间最短** 的任务开始执行。如果有多条执行时间相同的任务，则选择 **下标最小** 的任务。
3. CPU 一旦开始执行一个任务，就会一直执行到结束，不会被打断。
4. CPU 可以同时处理多个到达的任务（即在同一时刻有多个任务进入就绪状态）。

返回 CPU 处理任务的顺序（即任务的原始下标数组）。

## 解题思路

这是一道典型的 **“模拟 + 优先队列（小根堆）”** 题目。我们需要在时间推进的过程中，动态管理“已经到达但尚未执行”的任务。

### 核心步骤：
1. **记录原始下标并排序**：
   * 题目要求返回任务的原始下标。因此，我们需要把数组转换为 `[enqueueTime, processingTime, index]` 的三元组形式。
   * 按照**入队时间（enqueueTime）升序**对所有任务进行预排序，方便后续按时间线依次将任务加入就绪状态。

2. **使用优先队列（小根堆）管理就绪任务**：
   * 当 CPU 空闲时，所有在当前时间 `time` 之前已经到达的任务都可以被执行。
   * 在这些可执行任务中，CPU 优先选择 `processingTime` 最短的任务；若相同，则选择 `index` 最小的任务。
   * 我们可以使用一个小根堆来维护就绪任务，堆中的元素结构为 `(processingTime, index)`。

3. **时间线推进与模拟**：
   * 维护一个当前时间 `time`。
   * 如果当前堆为空，说明 CPU 处于空闲状态且没有就绪任务，此时可以直接将 `time` 快进到下一个未到达任务的 `enqueueTime`。
   * 将所有满足 $\text{enqueueTime} \le \text{time}$ 的任务压入堆中。
   * 从堆中弹出最优任务，更新 `time`（`time += processingTime`），并将该任务的下标记录到结果数组中。

## 代码实现 (Python)

```python
import heapq

class Solution:
    def getOrder(self, tasks: list[list[int]]) -> list[int]:
        n = len(tasks)
        # 1. 扩展任务数组，带上原始下标，并按入队时间升序排序
        extended_tasks = sorted(
            [(tasks[i][0], tasks[i][1], i) for i in range(n)],
            key=lambda x: x[0]
        )
        
        ans = []
        i = 0       # 指向扩展任务数组的指针
        time = 0    # 模拟的当前时间
        min_heap = [] # 小根堆：存放 (processingTime, index)
        
        while i < n or min_heap:
            # 如果堆为空，说明当前时间没有可执行任务，快进到下一个任务的到达时间
            if not min_heap:
                time = max(time, extended_tasks[i][0])
            
            # 将所有在当前时间之前（或刚好到达）的任务压入优先队列
            while i < n and extended_tasks[i][0] <= time:
                _, p_time, index = extended_tasks[i]
                heapq.heappush(min_heap, (p_time, index))
                i += 1
            
            # 取出最优任务执行
            p_time, index = heapq.heappop(min_heap)
            time += p_time  # 推进时间
            ans.append(index)
            
        return ans
```

### 复杂度分析

* **时间复杂度**：$O(N \log N)$
  * 对所有任务按照入队时间排序需要 $O(N \log N)$ 的时间。
  * 每个任务最多进堆和出堆一次，每次堆操作的时间复杂度为 $O(\log N)$，总共需要 $O(N \log N)$。
  * 因此总的时间复杂度为 $O(N \log N)$。

* **空间复杂度**：$O(N)$
  * 需要额外的空间存储扩展后的任务列表（大小为 $N$）以及优先队列（最多存储 $N$ 个元素），因此总体空间复杂度为 $O(N)$。

### 模拟运行 (Dry Run)

让我们用你给出的具体例子 `tasks = [[1,2],[2,4],[3,2],[4,1]]`，带上我们的代码，一步步进行模拟运行。

#### 准备工作：初始化与排序

* 任务 0：`[1, 2]` $\rightarrow$ 到达时间 1, 处理时间 2, 编号 0 $\rightarrow$ `(1, 2, 0)`
* 任务 1：`[2, 4]` $\rightarrow$ 到达时间 2, 处理时间 4, 编号 1 $\rightarrow$ `(2, 4, 1)`
* 任务 2：`[3, 2]` $\rightarrow$ 到达时间 3, 处理时间 2, 编号 2 $\rightarrow$ `(3, 2, 2)`
* 任务 3：`[4, 1]` $\rightarrow$ 到达时间 4, 处理时间 1, 编号 3 $\rightarrow$ `(4, 1, 3)`

`extended_tasks` 按到达时间排好序：
`[(1, 2, 0), (2, 4, 1), (3, 2, 2), (4, 1, 3)]`

* `i = 0`（指向第 0 个任务）

* **推进时间与记录**：
  * `time += 2` $\rightarrow$ `time` 变为 `1 + 2 = 3`。
  * `ans` 变为 `[0]`。

##### 【循环 2】
* **检查堆**：`min_heap` 当前为空（刚才弹出了唯一的任务 0）。
* **快进时间**：`time = max(3, extended_tasks[1][0])` $\rightarrow$ `max(3, 2) = 3`（此时 `time` 已经是 3 了，不需要倒退，保持 3）。
* **压入就绪任务**：此时 `time = 3`，所有到达时间 $\le 3$ 的任务有：
  * 任务 1 `(2, 4, 1)`（到达时间 2）
  * 任务 2 `(3, 2, 2)`（到达时间 3）
  * 把它们依次压入堆。堆会自动按处理时间排序：
  * 堆顶是处理时间较短的任务 2：`[(2, 2), (4, 1)]`
  * `i` 变为 3。
* **弹出最优任务**：从堆顶弹出 `(2, 2)`（处理时间 2，编号 2）。
* **推进时间与记录**：
  * `time += 2` $\rightarrow$ `time` 变为 `3 + 2 = 5`。
  * `ans` 变为 `[0, 2]`。

##### 【循环 3】
* **检查堆**：`min_heap` 还有剩余任务 `[(4, 1)]`（即任务 1），所以 `not min_heap` 为 `False`，不执行快进。
* **压入就绪任务**：此时 `time = 5`。在 `time <= 5` 范围内的还有任务 3 `(4, 1, 3)`（到达时间 4）。
  * 将其压入堆。此时堆里有：任务 1 `(4, 1)` 和任务 3 `(1, 3)`。
  * 堆顶自动调整为处理时间最短的任务 3：`[(1, 3), (4, 1)]`。
  * `i` 变为 4（所有任务都处理完了）。
* **弹出最优任务**：弹出 `(1, 3)`（处理时间 1，编号 3）。
* **推进时间与记录**：
  * `time += 1` $\rightarrow$ `time` 变为 `5 + 1 = 6`。
  * `ans` 变为 `[0, 2, 3]`。

##### 【循环 4】
* **检查堆**：`min_heap` 还有任务 `[(4, 1)]`（即任务 1），非空。
* **压入就绪任务**：`i = 4`（已经没有新任务了），内层循环跳过。
* **弹出最优任务**：弹出堆中仅剩的任务 1 `(4, 1)`（处理时间 4，编号 1）。
* **推进时间与记录**：
  * `time += 4` $\rightarrow$ `time` 变为 `6 + 4 = 10`。
  * `ans` 变为 `[0, 2, 3, 1]`。

* 循环结束（`i == 4` 且 `min_heap` 为空）。
* 返回 `ans = [0, 2, 3, 1]`，与题目给出的预期输出完全一致！

## LeetCode 1834（单线程 CPU）和 LeetCode 502（IPO）在核心思路上确实是双胞胎关系。

它们之所以看起来很像，是因为它们都属于同一类经典算法模型：“贪心策略 + 优先队列（堆）动态维护候选集”。

我们可以从以下几个维度来看看它们的异同点：

### 1. 核心骨架的相似性
这两道题的解题框架几乎一模一样：
* **前置排序**：都需要先把所有项目/任务按照某个时间点（IPO 是启动资金要求/利润，CPU 是入队时间）进行排序，用来控制“什么时候把新候选人加入人才市场（堆）”。
* **优先队列（堆）筛选**：都维护了一个堆，用来在“当前满足条件的候选池”中，以 $O(\log N)$ 的最高效率挑选出当前最优解（IPO 选利润最大的，CPU 选处理时间最短的）。
* **动态推进**：随着状态改变（资本增加 / 时间推移），不断解锁新的候选项目或任务。

### 2. 核心区别在哪里？

| 维度 | LeetCode 502. IPO | LeetCode 1834. 单线程 CPU |
| :--- | :--- | :--- |
| **驱动核心** | 资本（Capital） | 时间（Time） |
| **候选池触发条件** | 当你的总资本 $\ge$ 项目的启动资金时，项目入堆。 | 当当前时间 $\ge$ 任务的入队时间时，任务入堆。 |
| **堆的选择（贪心策略）** | 大根堆（Max-Heap）：因为我们要找利润最大的项目。 | 小根堆（Min-Heap）：因为我们要找**处理时间最短（或编号最小）**的任务。 |
| **推进机制** | 做完一个项目，资本增加，去解锁更多资本要求更低的项目。 | 结束一个任务，时间推进，去接纳在此时之前已经到达的新任务。 |

### 总结
你觉得它们像，说明你已经抓住了这类贪心+堆题目的底层逻辑：“按顺序解锁 $\rightarrow$ 扔进堆里 $\rightarrow$ 每次从堆里贪心地挑最优解”。掌握了这个套路，以后遇到类似“资源调度”、“动态规划候选集”的题目就能一眼看出解法了！

# LeetCode 79. 单词搜索 (Word Search)

## 题目描述

给定一个 $m \times n$ 二维字符网格 `board` 和一个字符串单词 `word`。如果 `word` 存在于网格中，返回 `true`；否则，返回 `false`。

单词必须按照字母顺序，通过相邻的单元格内的字母构成，其中“相邻”单元格是那些水平相邻或垂直相邻的单元格。同一个单元格内的字母不允许被在一个单词中重复使用。

## 解题思路

这是一道非常经典的 **回溯算法（Backtracking / 深度优先搜索 DFS）** 题目。我们需要在网格中寻找一条路径，使其按顺序连起来刚好等于给定的 `word`。

### 核心步骤：
1. **遍历起点**：
   * 我们可以把网格中的每一个格子都当作潜在的起点。只要某个格子的字符等于 `word` 的第一个字符，我们就从它开始进行深度优先搜索（DFS）。

2. **DFS 与递归匹配**：
   * 设计递归函数 `dfs(r, c, index)`：
     * `r, c`：当前所在的网格坐标。
     * `index`：当前正在匹配 `word` 里的第几个字符（下标）。
   * **终止条件**：如果 `index` 等于 `word` 的长度，说明 `word` 里的所有字符都已经成功匹配完毕，返回 `True`。

3. **剪枝与防重复访问（回溯的核心）**：
   * 如果当前坐标越界，或者当前格子的字符 `board[r][c]` 不等于 `word[index]`，说明此路不通，直接返回 `False`。
   * **修改现场**：为了防止在同一个单词中走回头路（即重复使用同一个格子），我们在进入当前格子时，将其临时修改为一个特殊字符（如 `'#'`）。
   * **向四个方向探索**：递归地向上下左右四个相邻格子查找下一个字符 `index + 1`。
   * **恢复现场（回溯）**：当四个方向都探测完准备离开当前格子时，必须把该格子原本的字符恢复（`board[r][c] = temp`），以免影响其他路线的搜索。

## 代码实现 (Python)

```python
class Solution:
    def exist(self, board: list[list[str]], word: str) -> bool:
        rows = len(board)
        cols = len(board[0])
        
        def dfs(r, c, index):
            # 1. 递归终止条件：index 达到单词长度，说明全部匹配成功
            if index == len(word):
                return True
            
            # 2. 边界检查与字符匹配检查
            if r < 0 or r >= rows or c < 0 or c >= cols or board[r][c] != word[index]:
                return False
            
            # 3. 标记当前格子已访问（防止走回头路）
            temp = board[r][c]
            board[r][c] = '#'
            
            # 4. 向四个方向（下、上、右、左）递归搜索下一个字符
            found = (
                dfs(r + 1, c, index + 1) or
                dfs(r - 1, c, index + 1) or
                dfs(r, c + 1, index + 1) or
                dfs(r, c - 1, index + 1)
            )
            
            # 5. 回溯：恢复当前格子的字符
            board[r][c] = temp
            
            return found

        # 遍历网格中的每一个格子作为起点
        for i in range(rows):
            for j in range(cols):
                if dfs(i, j, 0):
                    return True
                    
        return False
```

### 复杂度分析

* **时间复杂度**：O(M * N * 4^L)
  * 其中 $M$ 和 $N$ 分别为网格的行数和列数，$L$ 是单词 `word` 的长度。
  * 网格中共有 $M \cdot N$ 个起点。从每个起点出发，理论上最多有 4 个方向的扩散，递归深度最大为 $L$（即 $4^L$）。由于有提前剪枝和访问标记，实际运行效率远低于此理论上限。

* **空间复杂度**：O(L)
  * 主要开销来自于递归调用栈的深度，最大深度等于单词的长度 $L$。
* **空间复杂度**：O(L)
  * 主要开销来自于递归调用栈的深度，最大深度等于单词的长度 $L$。

## 一个非常关键、也经常让人卡壳的核心问题！

答案是：**它并不是“一下子把上下左右所有的路全部走完”，它只是“向前迈了仅仅一步”，然后通过递归不断重复这个过程。**

我们可以把这行代码拆解开来看看它到底是怎么运作的：

### 1. `dfs(...) or dfs(...)` 到底在干什么？

这四个 `dfs(...)` 并不是并排同时发生的，而是**按顺序依次尝试**的：

* **先试“向下走一步”**：`dfs(r+1, c, index+1)`
  * 如果这一步走下去，最后顺利找到了整个单词，那就直接返回 `True`，后面的方向就**不用试了**（短路求值）。
  * 如果向下走发现走不通（返回 `False`），那程序才会进行下一步。
* **再试“向上走一步”**：`dfs(r-1, c, index+1)`
  * 如果通了就返回 `True`，不通就继续。
* **接着试“向右走一步”**：`dfs(r, c+1, index+1)`
* **最后试“向左走一步”**：`dfs(r, c-1, index+1)`

所以，**每一次 `dfs` 调用，都只管“当前这一步”**。它把坐标往某个方向挪动了一格，把 `index` 加了 1，然后进入下一层函数去操心接下来的事情。

### 2. 为什么必须要写 `board[r][c] = temp`（恢复现场）？

这就是为什么**回溯（Backtracking）**算法必须要把格子改回去。

假设我们要找单词 `"ABCB"`，我们在网格里从 A 走到了 B，再走到了 C。

* **路径 A -> B -> C**：当我们走到 C 时，发现周围已经没有合法的 B 了（死胡同）。
* 这时，从 C 开始的这层 `dfs` 就要结束了，它会返回 `False`。
* **如果没有恢复现场**：刚才走过的 A、B、C 的格子全都被改成了 `'#'` 标记。
* 当程序退回到起点 A，准备尝试**另一条完全不同的路线**（比如从另一个方向去走别的 B 和 C）时，它会发现：“哎？怎么周围的 B 和 C 全都被改成 `'#'` 了？” 导致其他本来正确的路线无法通行！

所以，`board[r][c] = temp` 的意思是：
**“我从这个格子出发，四个方向（下、上、右、左）我都派侦察兵替我探过路了。不管它们成功还是失败，我现在的侦察任务结束了。我要把这个格子的路标擦干净（恢复原样），然后把结果（`found`）向上汇报。”**
