# 🔍 LeetCode 344. 反转字符串 (Reverse String) —— 对撞双指针流全解

## 一、 题目大意与核心约束
- **题目描述**：编写一个函数，其作用是将输入的字符串反转过来。输入字符串以字符数组 `s` 的形式给出。
- **核心约束**：
  - 必须**原地**修改输入数组（In-place）。
  - 额外空间复杂度必须限制在 **O(1)**。

## 二、 门派归类与物理直觉
- **门派归类**：**对撞双指针流 (Two Pointers: Opposing)**。
- **物理直觉**：
  - 让 `left` 指针站在数组头部（起点），`right` 指针站在数组尾部（终点）。
  - 两人同时向中间相向而行，每走一步就把 `s[left]` 和 `s[right]` 的数值进行交换（Swap）。
  - 当 `left >= right` 时，整个字符串正好翻转完毕，完美收工。

## 三、 Python3 高效通关源码

```python
class Solution(object):
    def reverseString(self, s):
        """
        :type s: List[str]
        :rtype: None Do not return anything, modify s in-place instead.
        """
        left = 0
        right = len(s) - 1
        
        while left < right:
            # 原地交换左右指针的字符
            s[left], s[right] = s[right], s[left]
            left += 1
            right -= 1
```

其实 344. Reverse String 完全可以用 Stack（栈）来解！ 

不仅能用，而且用栈的物理直觉（LIFO - 后进先出）来做反转字符串简直是天作之合。你可以把每一个字符依次压入栈中，然后再依次弹出来，弹出来的顺序自然就是倒过来的。

### 为什么在 LeetCode 官方要求里通常“不推荐”或“不直接”用栈？

虽然逻辑完全通，但在实际写代码时，用栈会面临两个硬伤：

1. **空间复杂度不达标（最大的痛点）**：
   - 题目对空间复杂度有严格的限制：要求原地修改（In-place），空间复杂度必须是 $O(1)$。
   - 如果你用一个标准的 Stack 数据结构（或者 Python 里的列表当栈用）把所有字符存一遍，额外空间复杂度就会变成 $O(N)$，这直接违背了题目 $O(1)$ 的空间约束。

2. **多此一举（失去了空间降维的优雅）**：
   - 用双指针（`left` 和 `right` 分别在两头往中间走，直接在原数组上做 `swap`）同样能达到 $O(N)$ 的时间，但空间可以直接压到 $O(1)$。
   - 相比之下，用栈不仅要额外开辟空间，最后还要把栈里的元素写回原数组，多绕了一圈。

### 用 Stack 的直观代码感受一下：

```python
class Solution(object):
    def reverseString(self, s):
        """
        :type s: List[str]
        :rtype: None Do not return anything, modify s in-place instead.
        """
        stack = []
        # 1. 压栈（LIFO）
        for char in s:
            stack.append(char)
            
        # 2. 出栈并写回原数组
        for i in range(len(s)):
            s[i] = stack.pop()
```

* 时间复杂度：$O(N)$
* 空间复杂度：$O(N)$ 

败就败在这里，因为额外用了栈的空间。所以，不是“不能用”，而是从面试工业级标准（要求 $O(1)$ 原地修改）的角度来看，双指针 swap 才是降维打击的正统解法，而栈在这里属于“大炮轰蚊子、空间超标”！

# 🔍 LeetCode 3. 无重复字符的最长子串 (Longest Substring Without Repeating Characters) —— 滑动窗口进阶流全解

## 一、 题目大意与核心约束
- **题目描述**：给定一个字符串 `s` ，请你找出其中不含有重复字符的**最长子串**的长度。
- **核心约束**：
  - 子串必须是连续的。
  - 要求时间复杂度为 O(N)，避免暴力双循环超时。

## 二、 门派归类与物理直觉
- **门派归类**：**滑动窗口与哈希索引跳转流 (Sliding Window & Hash Map)**。
- **物理直觉**：
  - 维持一个动态的窗口 `[left, right]` 代表当前的不重复子串。
  - 用一个哈希表（Dictionary）记录**字符最后一次出现的位置（下标）**。
  - **大步跃迁**：当右指针 `right` 遇到一个曾经出现过的重复字符时，左指针 `left` 不需要慢吞吞地一步步挪，而是直接**瞬移**到该重复字符上一次出现位置的下一个格子（`char_index_map[s[right]] + 1`），瞬间把重复元素甩在窗外！

## 三、 Python3 高效通关源码（Dict 索引优化版）

```python
class Solution(object):
    def lengthOfLongestSubstring(self, s):
        """
        :type s: str
        :rtype: int
        """
        char_index_map = {} # 记录字符及其最后一次出现的下标
        left = 0
        max_len = 0
        
        for right in range(len(s)):
            # 如果当前字符见过，且它的上次位置在当前窗口内（>= left）
            if s[right] in char_index_map and char_index_map[s[right]] >= left:
                # left 直接跳过重复字符的那一位，实现大步跃迁
                left = char_index_map[s[right]] + 1
                
            # 更新当前字符的最新下标
            char_index_map[s[right]] = right
            # 打擂台刷新最大长度
            max_len = max(max_len, right - left + 1)
            
        return max_len
```
`mymap[s[right]] = right` 这一步是整个哈希优化版滑动窗口的**灵魂落点**，它的核心作用有两个：

1. **实时更新/记录最新位置**：
   - 每次当右指针 `right` 扫描到一个字符 `s[right]` 时，无论这个字符之前有没有出现过，我们都要把它的**最新下标**（也就是当前的 `right`）更新到哈希表 `mymap` 里。
   - 这样能确保哈希表里存的永远是该字符**在整个字符串中最近一次出现的位置**。

2. **为后续的“大步跃迁”提供坐标支持**：
   - 当后面又遇到相同的字符时，我们在判断 `if s[right] in mymap and mymap[s[right]] >= left` 时，靠的就是这个字典里记录的下标。
   - 紧接着的下一行代码 `left = mymap[s[right]] + 1`，正是依赖了这一步存下来的 `right` 值，才能让 `left` 指针瞬间跳过重复字符，实现跳跃式前进，而不用慢吞吞地一位一位往右挪。
   
# 四、 复杂度核验 (Complexity Analysis)

- **时间复杂度**：$O(N)$，其中 $N$ 是字符串的长度。右指针 `right` 完整遍历了一遍字符串，左指针 `left` 只进不退，每个字符最多被访问一次，呈完美的线性时间。
- **空间复杂度**：$O(\min(N, \text{字符集大小}))$，哈希表最多存储当前窗口内或者整个字符集大小的键值对。

# 🔍 LeetCode 853. 车队 (Car Fleet) —— 排序贪心与单调栈流全解

## 一、 题目大意与核心约束
- **题目描述**：在一条单车道上有 `n` 辆车，它们朝同一个方向开往终点（目标位置为 `target`）。给定两个整数数组 `position`（车子的初始位置）和 `speed`（车子的行驶速度）。
  - 超车规则：车子不能超车。如果一辆车追上了前面的车，它会被迫降速，变成跟前面那辆车速度一样的“车队”一起前行。
- **核心问题**：求最后会到达终点多少个**车队**？

## 二、 门派归类与物理直觉
- **门派归类**：**排序贪心与逆向时间对比流 (Sorting & Greedy)**。
- **物理直觉**：
  - 如果从前往后（从起点到终点）模拟，后面的车随时可能合并，状态极其混乱。
  - **逆向思考**：我们把所有的车按照**初始位置从近到远（即离终点由近到远）**进行降序排序。
  - 离终点最近的车作为第一个领头羊，它的到达时间是绝对独立的。
  - 顺着往后看：拿后面每一辆车的单独到达时间，跟前面车（或车队）的到达时间作对比。如果后面的车到达时间 $\le$ 前面的车，说明它在半路会被追上并融合成同一个车队；如果大于前面的车，说明它追不上，会自立门户成为新的车队领头羊。

## 三、 Python3 高效通关源码

```python
class Solution(object):
    def carFleet(self, target, position, speed):
        """
        :type target: int
        :type position: List[int]
        :type speed: List[int]
        :rtype: int
        """
        # 1. 将车辆按起始位置打包，并从大到小排序（离终点最近的排在最前面）
        cars = sorted(zip(position, speed), reverse=True)
        
        fleet_count = 0
        prev_time = 0 # 记录前面车队到达终点所需的时间
        
        for pos, spd in cars:
            # 计算当前车单独开到终点需要的时间
            curr_time = float(target - pos) / spd
            
            # 如果当前车的到达时间大于前一个车队的到达时间，说明它无法被追上，自成一队
            if curr_time > prev_time:
                fleet_count += 1
                prev_time = curr_time  # 更新当前车队的时间标准
            # 否则（<= prev_time），说明它会在半路追上前车，并入当前车队，不需要增加车队计数
            
        return fleet_count
```

# 四、 复杂度核验 (Complexity Analysis)

- **时间复杂度**：$O(N \log N)$，其中 $N$ 是车的数量。主要的开销花在对车辆位置进行排序上，随后的遍历是线性 $O(N)$。
- **空间复杂度**：$O(N)$，用于存储打包后的车辆位置与速度数组。

# 🧠 853. Car Fleet 为什么用贪心？及贪心算法的五大门派

## 一、 853 为什么用贪心？贪心体现在哪里？

### 1. 为什么用贪心？
物理直觉上，后面的车如果开得比前面的车快，它并不能超车，而是会被迫降速、跟前面的车融合成一个“车队”。
如果我们从前往后（从起点到终点）去模拟这个过程会非常痛苦，因为前面任何一辆车的速度随时可能因为后面的加入而发生级联变化。
而**贪心思维**告诉我们：**我们只需要从“离终点最近的那辆车”开始逆向倒推**。离终点最近的领头羊它永远不会被任何人阻挡，它自己就是最直接的决策依据。

### 2. 贪心体现在哪里？
在这道题里，贪心极其优雅地体现在两个地方：
* **排序贪心（按离终点距离从近到远排序）**：我们优先处理最靠近终点的车。因为它的命运（到达时间）是绝对独立的，不受任何人影响。
* **局部最优推导全局独立（时间对比贪心）**：当处理后面的一辆车时，我们只需拿它单独到达终点的时间，跟前面那辆车（或者前面形成的整个车队）的时间作对比。
  - 如果后面的车到达时间 $\le$ 前面的车，说明它在半路一定会被追上，**贪心地让它并入当前车队**。
  - 如果后面的车到达时间 $>$ 前面的车，说明它追不上、成不了同一个车队，**贪心地让他自立门户，成为新的车队领头羊**。
这种“只看眼前、一步到位”的比较，完美符合贪心性质。

## 二、 贪心算法到底有多少不同类型？

在算法竞赛和面试中，贪心算法虽然没有像动态规划那样严谨的状态转移方程，但按照**思维切入点和应用场景**，通常可以划分为以下 **5 大主流类型**：

### 1. 排序贪心 (Sorting + Greedy) —— *853 属于这一类*
* **核心特征**：先把所有元素按照某种规则（如起点、终点、权重、性价比等）进行**排序**，然后从前往后或从后往前依次做出不可撤销的贪心决策。
* **经典代表**：
  * **Car Fleet（车队问题）**：按距离终点从近到远排序，比较到达时间。
  * **会议室/活动选择问题**：按结束时间从小到大排序，优先安排最早结束的活动，从而腾出最多时间。

### 2. 区间贪心 (Interval Greedy)
* **核心特征**：处理数轴上的区间覆盖、区间选点、不相交区间等问题。
* **经典代表**：
  * **用最少数量的箭引爆气球 (Burst Balloons / Interval Stabbing)**：按气球右边界排序，贪心地在每个气球右边界射出一箭。
  * **合并区间 / 无重叠区间**。

### 3. 字典序贪心 (Lexicographical Greedy)
* **核心特征**：在构造字符串或数组时，为了让整体字典序最大或最小，每一位都贪心地去争取当前能达到的极致字符/数字。
* **经典代表**：
  * **去除 K 位数字**：利用单调栈，每次让高位的数字尽可能小。
  * **拼接最大数**。

### 4. 反悔贪心 (Regret / Exchange Greedy)
* **核心特征**：初看是普通的贪心，但在遇到更优解时，允许通过一个数据结构（通常是**优先队列/堆**）把前面已经做出的“较劣选择”给**吐出来（反悔）**，换成更优的选择。这是贪心里的高级大招。
* **经典代表**：
  * **工作安排 / 股票买卖最大化利润**。

### 5. 数学与博弈贪心 (Mathematical & Game Theory Greedy)
* **核心特征**：依赖严格的数学推导或局部最优的博弈性质（如奇偶性、前缀和极值、绝对值不等式）。
* **经典代表**：
  * **跳跃游戏 (Jump Game)**：每一步贪心地计算当前能跳到的最远边界（`max_reach`）。

# 🔍 LeetCode 71. 简化路径 (Simplify Path) —— 栈与路径解析流全解

## 一、 题目大意与核心约束
- **题目描述**：给你一个字符串 `path` ，表示指向某一文件或目录的 Unix 风格的**绝对路径**（以 `'/'` 开头），请你将其转化为更加简洁的规范路径。
- **Unix 路径规则核心要点**：
  - `.` 表示当前目录本身。
  - `..` 表示将目录切换到上一级目录（父目录）。
  - 任意多个连续的斜杠（如 `//`）都被视为一个单独的斜杠 `/`。
  - 规范路径必须以 `/` 开头，两个目录名之间必须只有一个 `/`，最后一个目录名不能以 `/` 结尾（除非路径是根目录 `/`）。
  - 规范路径中不包含任何 `.` 或 `..`。

## 二、 门派归类与物理直觉
- **门派归类**：**栈与字符串分割流 (Stack & String Parsing)**。
- **物理直觉**：
  - 想象我们在用命令行（Terminal）进入深层文件夹。
  - 当我们看到普通的目录名时，就像是“**进门**”（压入栈中）。
  - 当我们看到 `.` 时，就像是“**原地踏步**”（忽略不管）。
  - 当我们看到 `..` 时，就像是“**退房/返回上一层**”（栈顶元素弹出）。
  - 整个过程后进先出（LIFO），用**栈（Stack）**来管理目录层级简直是天作之合。

## 三、 Python3 高效通关源码

```python
class Solution(object):
    def simplifyPath(self, path):
        """
        :type path: str
        :rtype: str
        """
        # 1. 按照斜杠 '/' 将路径分割成各个片段
        # 例如 "/a//b/./c/../" 分割后会有很多空字符串 "" 以及 "." 和 ".."
        parts = path.split('/')
        
        stack = []
        for p in parts:
            # 如果是空字符串，或者当前目录 '.'，直接跳过
            if not p or p == '.':
                continue
            elif p == '..':
                # 如果是上一级目录，且栈不为空，则退栈（返回上一层）
                if stack:
                    stack.pop()
            else:
                # 普通目录名，压入栈中（进入下一层）
                stack.append(p)
                
        # 2. 将栈里保存的有效目录用 '/' 拼接起来，前面补上根目录
        return '/' + '/'.join(stack)
```

# 四、 复杂度核验 (Complexity Analysis)

- **时间复杂度**：O(N)，其中 $N$ 是字符串的长度。我们需要对路径进行一次 `split` 切割，然后遍历所有切出来的片段，入栈出栈均为均摊 $O(1)$。
- **空间复杂度**：O(N)，用于存储分割后的片段数组以及栈中保留的有效目录名。

### 4. 处理片段：`'Documents'`

用 `'/'` 将它们拼接起来，并在最前面补上根目录 `/`：
`'/' + '/'.join(['home', 'user', 'Pictures'])` $\rightarrow$ **`/home/user/Pictures`**


## return '/'+'/'.join(stack), 

其实，**`'/'.join(stack)` 本身是完全对的（它是核心拼接逻辑）**，但如果直接写成 `return '/'.join(stack)`，在某些特定情况下就会翻车。

咱们来看看为什么代码里要在前面加一个根目录斜杠：**`return '/' + '/'.join(stack)`**。

### 💥 如果只写 `'/'.join(stack)` 会发生什么？

假设最终栈里剩下的有效目录是 `['home', 'user']`：
- 如果你直接用 `'/'.join(['home', 'user'])`，得到的结果是：
  - **`'home/user'`** ❌
- 细看这个结果：**它少了一个最开头的根目录斜杠 `/`**！
- 在 Unix 路径规范里，绝对路径必须以 `/` 开头。

### ✨ 加上 `'/' +` 之后呢？
- `'/' + 'home/user'` ➔ **`/home/user`** ✅ 完美符合绝对路径规范。

### 🧐 那什么情况下只用 `'/'.join(stack)` 刚好能对？
只有当栈是**空栈**时（也就是路径被简化到了只剩根目录，比如 `path = "/../"`）：
- 此时 `stack = []`。
- `'/'.join([])` 的结果是空字符串 `""`。
- 如果我们写 `'/' + ""`，结果就是 **`/`**，正好是根目录。
- **反过来**：如果硬核地只写 `'/'.join(stack)`，空栈时拼出来的就是空字符串 `""`，这在 LeetCode 上会直接报错，因为根目录必须是 `/` 而不是空串！

所以，老铁，`'/'.join(stack)` 是拼接的主力，但前面必须加上 `'/'` 托底，才能保证无论栈空还是栈满，输出的永远是标准的绝对路径！🚀🔥

### LeetCode 71: Simplify Path (数据流版本 / Stream Version)

如果输入不是一次性给出的静态字符串，而是一个**动态流淌的字符数据流**（例如通过网络 Socket、文件读取流、或者逐个吐出字符的管道），我们就不能再用全局的 `split('/')` 来处理。

此时的核心思路是：**用一个缓冲区（Buffer）暂存当前正在读取的目录名字符，用栈（Stack）维护当前的目录层级，遇到 `/` 就触发结算。**

#### 核心代码实现 (Python)

```python
class StreamPathSimplifier:
    def __init__(self):
        self.stack = []
        self.buffer = []  # 暂存当前未结算的目录名字符

    def read_char(self, char: str):
        """模拟从数据流中逐个读取字符"""
        if char == '/':
            # 遇到斜杠，说明前一个目录名结束了，结算 buffer
            self._process_buffer()
        else:
            # 收集目录名的字符
            self.buffer.append(char)

    def flush(self):
        """数据流结束时，处理残留在 buffer 里的最后一个目录名"""
        self._process_buffer()

    def _process_buffer(self):
        """核心逻辑：对缓冲区里的字符串进行路径规则判断并入栈/出栈"""
        if not self.buffer:
            return  # 连续的斜杠（比如 '//'）会导致 buffer 为空，直接跳过

        component = "".join(self.buffer)
        self.buffer = []  # 清空缓冲区，为下一个目录名做准备

        if component == "..":
            if self.stack:
                self.stack.pop()
        elif component != ".":
            self.stack.append(component)

    def get_simplified_path(self) -> str:
        """随时获取当前的简化绝对路径"""
        return "/" + "/".join(self.stack)


# ==================== 测试数据流模拟 ====================
stream_sim = StreamPathSimplifier()

# 假设数据流里的字符是一个接一个流进来的："/a/./b/../../c/"
data_stream = "/a/./b/../../c/"

for ch in data_stream:
    stream_sim.read_char(ch)

# 数据流结束，刷新结尾
stream_sim.flush()

print(stream_sim.get_simplified_path())  # 输出: "/c"
```

### 数据流处理的关键改动点

* **放弃全局 `split('/')`**：因为数据流是动态流淌的，无法在开头执行全局切分，必须改用 **Buffer（缓冲区）** 边读边攒，遇到 `/` 再触发结算。
* **栈（Stack）维持不变**：依然用来完美处理 `..` 回退上一级目录的逻辑。
* **处理结尾闭环 (`flush`)**：数据流结束时可能没有以 `/` 结尾，因此需要调用一次 `flush()` 把缓冲区里最后剩下的残余字符结算进栈。

### 🧠 附加题:

题目大意解析: 这道题用最白话、最直观的语言来翻译，意思是这样的：

#### 1. 规则（Operation）：
给你一个包含 $n$ 个整数的数组。在每一次操作中，你可以**选择两个不同的数字 $x$ 和 $y$，把数组里所有的 $x$ 全部变成 $y$**。
> *(注意：这类似于“合并同类项”或者“染色”，把某种颜色的珠子全换成另一种颜色。)*

#### 2. 目标（Goal）：
通过若干次这样的操作，让数组中**每一个不同的数值都聚集成连续的一块（contiguous block）**。
* **什么叫连续的一块？** 比如 `[1, 1, 2, 2, 3]` 里面，数字 1 在一起、2 在一起、3 在一起，它们各自都是连续的，不需要再变了，所以答案是 `0` 次操作。
* 最终要让你**返回所需的最少操作次数**。


### 🔍 举个例子看懂它

#### 🌰 例子 1：`[1, 1, 2, 2, 3]`
* **现状**：数字 1 连在一起，2 连在一起，3 连在一起。
* **结果**：已经满足所有不同值各自连续。
* **操作次数**：`0`

#### 🌰 例子 2：`[1, 2, 1, 3]`
* **现状**：数字 1 被数字 2 隔开了（分成了两段：头尾有 1，中间有 1），不连续。
* **怎么用 1 次操作搞定？**
  * 你可以选择把所有的 `2` 变成 `1`（或者把某个 1 变成别的），但最聪明的做法是：**把中间的那个 `2` 变成 `1`**（或者把所有的 2 融进 1 里）。
  * 如果把中间的 `2` 变成 `1`，数组就变成了 `[1, 1, 1, 3]`。
  * 此时：连续的 `1` 块，和连续的 `3` 块。所有不同值都各自连在一起了！
* **操作次数**：`1`

### 💡 核心规律揭秘（最后一行注释的意思）

代码最后一行注释写着：`# k distinct value -> k - 1 operation`
意思是：**如果数组里一共有 $k$ 个不同的数值，那么最多只需要 $k - 1$ 次操作就能搞定。**

* 为什么？因为你只要选定一个“主基调”数字，把其余剩下的 $k-1$ 个不同的数字依次“并入”或“消灭”掉，每次操作消灭一个不同的数值，一共进行 $k-1$ 次就能让所有元素融合成合理的连续区块。

面对一道算法题却完全没有思路时，不要慌，这是刷题过程中非常正常的现象。资深程序员和算法工程师在遇到新题时，也有一套标准、系统化的“解题方法论”来反推应该用什么算法。

当你不知道用什么方法时，可以通过以下四个步骤进行排查和选择：

### 第一步：从“数据规模（Time Complexity / Constraints）”反推算法
这是最快锁定算法范围的“作弊器”。看一眼题目给出的数据范围（$n$ 的大小），通常就能直接排除掉大半错误选项：

* **$n \le 10$ 阶乘级别 ($O(n!)$)**：
  * 必定是：全排列、状态压缩。
* **$n \le 20$ 指数级别 ($O(2^n)$)**：
  * 必定是：回溯（Backtracking）、状态压缩 DP、深度优先搜索（DFS）。
* **$n \le 100 \sim 400$ 三次方级别 ($O(n^3)$)**：
  * 通常是：动态规划（区间 DP）、弗洛伊德算法（Floyd）。
* **$n \le 3000 \sim 10000$ 平方级别 ($O(n^2)$)**：
  * 通常是：二维动态规划、两层嵌套循环遍历、简单的图论。
* **$n \le 10^5 \sim 10^6$ 线性或线性对数 ($O(n)$ 或 $O(n \log n)$)**：
  * 通常是：排序（Sorting）、双指针（Two Pointers）、滑动窗口（Sliding Window）、单调栈/单调队列、堆（Heap）、贪心（Greedy）、哈希表（Hash Map）或二分查找。
* **$n \ge 10^9$ 对数级别 ($O(\log n)$)**：
  * 通常是：二分查找（Binary Search）、数学规律、位运算。

### 第二步：从“题目关键词与要求”定位核心数据结构
题目的字里行间往往暗含了出题人的意图，观察关键词：

* **关键词：“连续子数组 / 子串 / 最大最小窗口”** $\to$ 优先考虑 **滑动窗口 (Sliding Window)** 或 **前缀和 (Prefix Sum)**。
* **关键词：“有序数组 / 查找某个值或区间”** $\to$ 优先考虑 **二分查找 (Binary Search)** 或 **双指针 (Two Pointers)**。
* **关键词：“最近的 / 下一个更大 / 括号匹配”** $\to$ 联想到 **栈 (Stack)**（尤其是单调栈）。
* **关键词：“层序遍历 / 最短路径（无权图） / 扩散”** $\to$ 优先考虑 **广度优先搜索 (BFS)**。
* **关键词：“所有可能解 / 组合 / 子集 / 棋盘搜索”** $\to$ 优先考虑 **回溯 (Backtracking / DFS)**。
* **关键词：“最大/最小利润 / 最优解 / 子问题最优”** $\to$ 优先考虑 **贪心 (Greedy)**（局地最优）或 **动态规划 (DP)**（全局最优）。
* **关键词：“动态连接 / 朋友圈 / 连通分量”** $\to$ 考虑 **并查集 (Union-Find)**。

### 第三步：如果还不知道，尝试“暴力解法 (Brute Force)”并优化
如果前两步还没头绪，**先写出最笨的暴力解法**：

1. 暴力解法通常是双重循环 $O(n^2)$ 或递归穷举。
2. 写出暴力解后，问自己一个问题：**“重复计算了什么？瓶颈在哪里？”**
   * 如果重复计算了重叠子问题 $\to$ **引入记忆化搜索或动态规划 (DP)**。
   * 如果在有序结构中反复做线性查找 $\to$ **改成二分或哈希表降维 ($O(1)$ 或 $O(\log n)$)**。
   * 如果需要频繁求某个动态区间的最值 $\to$ **引入堆 (Heap) 或线段树**。

### 第四步：横向类比（经典套路联想）
平时刷题时，注意归纳题型。绝大多数 LeetCode 题目都是经典模型的变形：

* 遇到求方案总数、能不能凑成 $\to$ **背包 DP / 计数 DP**。
* 遇到股票买卖、打家劫舍、最长递增子串 $\to$ **状态机 DP 或一维 DP**。
* 遇到图论遍历 $\to$ **先分清是拓扑排序、Dijkstra 还是并查集**。

> **总结成一句话**：做不出题时，先看 **$n$ 的大小**卡复杂度，再看 **求什么**（最值、方案数、是否存在），最后从 **暴力解的痛点** 去找优化方向。

### 💡 以刚才那道算法题为例：四步解题方法论实战

我们可以用刚才截图里看到的这道算法题（**“使同类元素连续的最少操作次数”**），来实战演练一下这套“四步解题方法论”：

### 第一步：从“数据规模（Time Complexity / Constraints）”反推算法
* **观察点**：虽然题目截图里没有完整写出 $n$ 的具体上限，但在正常的 LeetCode 类似题目中，这类涉及数组元素替换和连续合并的题目，$n$ 通常在 $10^4$ 到 $10^5$ 的量级。
* **锁定目标**：
  * 如果 $n$ 是 $10^5$ 级别，说明 $O(n^2)$ 的暴力解法（两层循环枚举每个元素怎么变）大概率会超时（Time Limit Exceeded）。
  * 我们的算法必须控制在 **$O(n)$ 或 $O(n \log n)$** 的时间复杂度内。
  * 这直接帮我们排除了回溯、全排列（那些适合 $n \le 20$ 的指数级算法），把方向锁定在了**哈希表、双指针、滑动窗口或贪心/排序**上。

### 第二步：从“题目关键词与要求”定位核心数据结构
* **观察题目给的规则**：
  * 关键字：“`change all occurence of x to y`”（把所有的 $x$ 变成 $y$）
  * 关键字：“`make each distinct value in continous block`”（让每个不同的值在数组里自成一个连续块）
* **与常规关键词对比**：
  * 我们发现它**没有**出现“连续子数组/子串”（排除了滑动窗口）。
  * 但它涉及了“**不同的数值（distinct value）**”和“**全局替换合并**”。
  * 这提示我们：我们需要统计数组中有哪些不同的数（可以用哈希表 `Set` 或字典），并且去观察它们在数组中第一次出现和最后一次出现的位置（即每个数字的**区间跨度**），看看它们之间是如何交织在一起的。

### 第三步：如果还不知道，尝试“暴力解法 (Brute Force)”并优化
* **最笨的暴力思路**：
  * 穷举所有可能的替换顺序：先挑两个数 $x$ 和 $y$ 合并，看看数组变成什么样，然后再挑另外两个数……直到所有数都连续。这显然是个组合爆炸问题。
* **分析痛点与瓶颈**：
  * 暴力解法的痛点在于**每次全局替换后，整个数组都被改动了，状态极难维护**。
  * **反向思考（转换视角）**：与其去模拟“怎么把 $x$ 变成 $y$”，不如换个角度想——**什么情况下我们不需要对某个数字动手？**
  * 如果一个数字的所有出现位置本身就已经聚集成了一个连续的区间，且中间没有被太多“其他乱七八糟的数字”死死卡住，或者我们可以通过某种贪心策略，保留某一个最“省事”的数字不动，让其他的数字向它靠拢。
  * 根据题目最后给出的神仙规律：`# k distinct value -> k - 1 operation`（有 $k$ 个不同的值，最多只需要 $k-1$ 次操作）。这说明最终的操作上限被锁死在了“不同数值的个数”上。

### 第四步：横向类比（经典套路联想）
* **联想经典题型**：
  * 这类“通过替换或合并元素来达到某种连续状态 / 最少操作数”的题目，本质上和**区间重叠（Interval Merging）**、**离散化处理**或者**图的连通块划分**高度相似。
  * 它的核心考点不是去真正的“动手修改数组里的每一个数”，而是去考察**不同数值之间的包含、相交和夹逼关系**。
  * 最终的最优解法通常是：用哈希表记录每个数字的起始和结束位置，找出那些能够“顺便”被包含进大区间里的元素，从而用 $k - 1$ 推导出最少步数。
