# 703. Kth Largest Element in a Stream

- **LeetCode 链接**: [Kth Largest Element in a Stream](https://leetcode.com/problems/kth-largest-element-in-a-stream/)
- **难度**: Easy
- **核心考点**: 数据流处理 / 堆 (Min-Heap) / Top-K 问题

## 1. 题目直觉与场景还原

> **用一句话解释**：设计一个实时排行榜，每次有新成绩加进来，立刻报出“第 $k$ 名”是谁。

### 场景推导（以 $k = 3$ 为例）
时刻追踪全场第 3 名的成绩：

1. **初始池子**：`[4, 5, 8, 2]`
   - 从大到小排序：`8, 5, 4, 2`
   - 前 3 名是 `[8, 5, 4]`，其中第 3 名是 **4**。
2. **调用 `add(3)`**：新加入一个成绩 3
   - 当前所有成绩：`8, 5, 4, 3, 2`
   - 前 3 名依然是 `[8, 5, 4]`，第 3 名依然返回 **4**。
3. **调用 `add(5)`**：新加入一个成绩 5
   - 当前所有成绩：`8, 5, 5, 4, 3, 2`
   - 前 3 名变成了 `[8, 5, 5]`，第 3 名被刷新为 **5**。
4. **调用 `add(10)`**：新加入一个高分 10
   - 前 3 名变成了 `[10, 8, 5]`，第 3 名依然是 **5**。
5. **调用 `add(9)`**：新加入一个高分 9
   - 前 3 名变成了 `[10, 9, 8]`，第 3 名被刷新为 **8**。

## 2. 为什么暴力解法不行？

- **暴力做法**：每次调用 `add()`，把新数字追加到数组末尾，然后重新整体排序 `sort()`，返回倒数第 $k$ 个数。
- **致命缺陷**：数据流会不断调用 `add()`。假设调用 $M$ 次，每次排序耗时 $O(N \log N)$，总时间复杂度高达 $O(M \cdot N \log N)$，直接引发超时（TLE）。

## 3. 核心破局点：维护大小为 $k$ 的“最小堆”（Min-Heap）

求“第 $k$ 大”，直觉上容易联想到大顶堆，但**最优解法是维护一个容量上限为 $k$ 的最小堆**：

- **逻辑本质**：
  - 我们根本不关心比第 $k$ 名更差的人（第 $k+1$ 名及之后可以直接丢弃）。
  - 我们只维护一个“VIP 俱乐部”，这个俱乐部**永远只保留全场最强的 $k$ 个人**。
- **为什么用最小堆？**
  - 在这 $k$ 个顶尖元素的集合中，堆顶存放的是**该集合中的最小值**。
  - 这个处于门槛位置的最小值，在全局视角下正好就是**全场第 $k$ 大的元素**。

## 4. 算法运转流程

1. **初始化 `__init__`**：
   - 将现有数组转为堆结构，多余的元素弹出，直到堆的大小缩小到 $k$。
2. **调用 `add(val)`**：
   - 将新元素入堆：`heapq.heappush(self.min_heap, val)`。
   - 检查堆容量：若堆大小超过 $k$，弹出堆顶最小值：`heapq.heappop(self.min_heap)`。
   - 此时堆顶 `self.min_heap[0]` 即为当前流中的第 $k$ 大元素。

## 5. 代码实现 (Python3)

```python
import heapq
from typing import List

class KthLargest:

    def __init__(self, k: int, nums: List[int]):
        self.k = k
        self.min_heap = nums
        heapq.heapify(self.min_heap)
        
        # 保持堆的容量不超过 k
        while len(self.min_heap) > self.k:
            heapq.heappop(self.min_heap)

    def add(self, val: int) -> int:
        heapq.heappush(self.min_heap, val)
        
        # 超过容量则淘汰最小值
        if len(self.min_heap) > self.k:
            heapq.heappop(self.min_heap)
            
        # 堆顶即为第 k 大元素
        return self.min_heap[0]
```

## 6. 复杂度分析

- **时间复杂度**:
  - **初始化 `__init__`**: $O(N \log k)$ 或建堆 $O(N) + (N - k) \log N$。总耗时可控制在 $O(N \log k)$。
  - **单次 `add` 操作**: 堆的大小恒定 $\le k$，入堆与出堆耗时均为 $O(\log k)$，读取堆顶为 $O(1)$。若调用 $M$ 次 `add`，总耗时为 $O(M \log k)$。
- **空间复杂度**: $O(k)$。堆中仅保留 $k$ 个元素，消耗与数据流总长度无关的固定空间。

### 一、 单次 add 操作为什么是 $O(\log k)$？

因为我们限制了堆的最大容量永远只有 $k$：

* **二叉堆的高度**：一个拥有 $k$ 个元素的完全二叉树（堆），其树的高度是 $\log_2 k$。
* **入堆与出堆机制**：
  * `heappush(val)`：把新元素放在树底，沿路径向上调整（Sift Up），最多走整棵树的高度，即 $\log k$ 步。
  * `heappop()`：把堆顶拿走，将末尾元素移到堆顶并向下调整（Sift Down），同样最多走整棵树的高度，即 $\log k$ 步。
* **读取堆顶**：堆顶就是数组第 0 个元素 `heap[0]`，直接寻址，耗时 $O(1)$。
* **总耗时**：单次 `add` 做了常数次堆操作，所以单次代价是 $O(\log k)$；如果调用了 $M$ 次，总代价就是 $O(M \log k)$。

### 二、 初始化 __init__ 的复杂度是怎么来的？

初始数组有 $N$ 个元素，我们有两种构建方式：

**方式 1：逐个插入（动态维护大小为 $k$ 的堆）**
* 从前往后遍历 $N$ 个数，每来一个数就 push 进堆，一旦大小超过 $k$ 就 pop 掉。
* 堆的大小始终被压制在 $k$ 以内，因此每次插入/弹出的成本都不会超过 $O(\log k)$。
* 一共处理 $N$ 个数，总耗时就是稳稳的 $O(N \log k)$。

**方式 2：先原地建堆，再弹出多余元素（即上面写的第二种推导）**
* **原地建堆 `heapq.heapify(nums)`**：
  Python 底层使用的是 Floyd 建堆算法（自底向下调整），直接把包含 $N$ 个元素的列表在原地调整成堆，这一步耗时是 $O(N)$（而不是很多人直觉上的 $N \log N$）。
* **弹出多余元素**：
  堆里原来有 $N$ 个数，我们要保留前 $k$ 个，就需要连续执行 $(N - k)$ 次 `heappop()`。
  每次 pop 时，堆的大小在从 $N$ 逐渐缩减到 $k$。每次弹出需要走树高 $O(\log N)$。
  所以弹出多余元素消耗的时间是 $(N - k) \log N$。
* **两者相加**：
  $$\text{总耗时} = O(N) + (N - k) \log N$$

### 两种写法的本质对比

* 当 $k \ll N$（比如 $N = 10^5, k = 5$）：
  * 方式 1 只需要 $O(N \log 5)$，非常轻量。
  * 方式 2 要 pop 掉几乎全部元素，花了大量的 $(N - k) \log N$ 时间。
* 两种方式在大量工业库或面试手写中都很常见，但结论是一致的：只要在初始化阶段把堆的规模压到 $k$ 以内，后续所有的 `add` 就能稳定享受 $O(\log k)$ 的低开销。
