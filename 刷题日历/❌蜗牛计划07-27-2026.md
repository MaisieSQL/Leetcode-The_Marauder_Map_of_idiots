# 📝 LeetCode 217. 存在重复元素 (Contains Duplicate) 题目解析

## 1. 题目大意
- **原题描述**：给你一个整数数组 `nums`。如果数组中任一值出现**至少两次**，返回 `true`；如果数组中每个元素互不相同，返回 `false`。
- **输入输出示例**：
  - 输入：`nums = [1, 2, 3, 1]` -> 输出：`True`（因为 `1` 重复出现了）
  - 输入：`nums = [1, 2, 3, 4]` -> 输出：`False`（全员各不相同）

## 2. 核心考点与物理直觉
- **核心考点**：哈希表（Hash Map / 键值对映射）、线性扫描。
- **物理直觉**：
  - 最笨的方法是拿每一个数字去和它后面的所有数字做对比（暴力双循环），时间复杂度直接飙升到 $\mathcal{O}(N^2)$，数据量大时铁定超时。
  - **降维打击策略**：利用**标准哈希表（Hash Map）**。我们在遍历数组的过程中，把见过的数字当作 `Key` 存入哈希表中。每遇到一个新数字，先去哈希表里“照镜子”：
    - 如果在哈希表里找到了，说明**撞车（重复）**，直接鸣金收兵返回 `true`。
    - 如果没找到，就把它登记录入哈希表，继续往下走。

## 3. 标准哈希表（Hash Map）解法源码 (Python3)

```python
class Solution:
    def containsDuplicate(self, nums: List[int]) -> bool:
        # 声明一个标准的哈希表（Hash Map / 字典），用于记录数字及其出现状态
        freq_map = {}
        
        for num in nums:
            # 如果当前数字已经在哈希表中，说明之前见过了，触发重复判定
            if num in freq_map:
                return True
            
            # 首次遇到，将其登记进哈希表（赋予一个占位 Value 1）
            freq_map[num] = 1
            
        # 完整遍历完数组都没有触发返回，说明没有任何重复元素
        return False
```

4. 复杂度深度核验
- **时间复杂度**：O(N) —— 只需要对数组进行单次线性扫描（N 为数组长度）。标准哈希表的单次查找 (`in`) 和单次插入操作的均摊时间复杂度均为 O(1)。
- **空间复杂度**：O(N) —— 在最坏情况下（即整个数组完全没有重复元素），我们需要把所有的 N 个元素全部存入哈希表中，因此需要消耗线性的存储空间。

# 📝 LeetCode 912. 排序数组 (Sort an Array) 题目解析

## 1. 题目大意
- **原题描述**：给你一个整数数组 `nums`，请你将该数组升序排列。
- **硬性约束**：必须在 O(N log N) 的时间复杂度内完成，且尽量使用较好的空间复杂度。不能直接依赖 Python 自带的无脑 `nums.sort()`（虽然能过，但面试官通常要求手写经典排序算法）。

## 2. 核心考点与物理直觉
- **核心考点**：分治思想 (Divide and Conquer)、归并排序 (Merge Sort)。
- **物理直觉**：
  - 如果数组很乱、很长，直接整体排序很难下手。
  - **“分而治之” (Divide and Conquer)** 的核心哲学：
    1. **分 (Divide)**：把一个大数组从中间一刀切两半（`left` 和 `right`），一直递归切到每个子数组只剩 1 个元素（此时天然有序）。
    2. **治 (Conquer/Merge)**：把两个已经有序的小数组，通过**双指针**像拉拉链一样完美合流成一个更大的有序数组，一路向上合并，直到恢复成完整的大数组。

## 3. 标准归并排序解法源码 (Python3)

```python
class Solution:
    def sortArray(self, nums: List[int]) -> List[int]:
        # 递归出口：当数组长度小于或等于 1 时，本身就是有序的，直接返回
        if len(nums) <= 1:
            return nums
        
        # 1. 分 (Divide)：找到中点，一分为二
        mid = len(nums) // 2
        left = self.sortArray(nums[:mid])
        right = self.sortArray(nums[mid:])
        
        # 2. 治 (Merge)：将左右两个有序数组合流
        return self.merge(left, right)
        
    def merge(self, left: List[int], right: List[int]) -> List[int]:
        res = []
        i = j = 0
        
        # 双指针像拉拉链一样，谁小先拿谁
        while i < len(left) and j < len(right):
            if left[i] <= right[j]:
                res.append(left[i])
                i += 1
            else:
                res.append(right[j])
                j += 1
                
        # 把没走完的尾巴直接拼接到末尾
        res.extend(left[i:])
        res.extend(right[j:])
        return res

```

4. 复杂度深度核验
- **时间复杂度**：O(N log N) —— 递归树的高度为 log N（每次对半拆分），每一层在合并所有元素时需要进行线性的 O(N) 扫描，总时间复杂度稳稳锁定在 O(N log N)。
- **空间复杂度**：O(N) —— 递归调用栈会消耗 O(log N) 的栈空间，同时在每次归并时需要创建临时列表来存储合并后的数据，因此整体空间复杂度主要由临时存储决定，为 O(N)。

### 归并排序（Merge Sort）时间复杂度：$O(n \log n)$ 递归树推导

#### 1. 递归树的结构与高度
* **拆分过程**：假设原数组长度为 $n$。
  * 第 0 层：1 个长度为 $n$ 的数组
  * 第 1 层：2 个长度为 $n/2$ 的子数组
  * 第 2 层：4 个长度为 $n/4$ 的子数组
  * ……
  * 第 $k$ 层：$2^k$ 个长度为 $n / 2^k$ 的子数组
* **树的高度（总层数）**：当子数组长度被切分到只剩 1 个元素时停止。从 $n$ 不断除以 2 直到变成 1，总共需要切分 $\log_2 n$ 次。因此，树的深度（层数）为 **$\log n$**。

#### 2. 每一层的合并总工作量
在递归树的**任意一层**中，虽然数组被分成了许多小块，但把这一层**所有小块的长度加起来，总和永远是 $n$**。

`merge` 函数在每一层的作用，就是把这些相邻的已排序小块归并组合起来。因此：
* **每一层的总工作量** = 节点数 $\times$ 每个节点的工作量
  * 第 0 层：$1 \times n = n$
  * 第 1 层：$2 \times (n / 2) = n$
  * 第 2 层：$4 \times (n / 4) = n$
  * ……
  * 第 $k$ 层：$2^k \times (n / 2^k) = n$

> **结论**：不管在哪一层，每一层的总工作量都是恒定的 **$n$**。

#### 3. 总时间复杂度计算
总工作量等于**“每一层的工作量”**乘以**“总层数”**：

$$\text{总工作量} = n \times \log n = O(n \log n)$$

由于归并排序在最好、最坏和平均情况下，都严格执行同样深度的二分与合并，因此其**时间复杂度稳定为 $O(n \log n)$**。

# ⚖️ 排序算法大乱斗：为什么 LeetCode 912 选“分治/归并”，不用其他算法？

## 一、 为什么选“分治（归并排序）”？它好在哪？
在 LeetCode 912（排序数组）中，归并排序（Merge Sort）之所以是标准推荐解法之一，核心原因有两点：
1. **最坏情况下的绝对稳定性**：它的时间复杂度在**最好、平均、最坏情况下全都是 O(N log N)**，绝不会因为数据本身长得奇葩而退化成 O(N²)。
2. **稳定的排序（Stable Sort）**：如果两个元素值相同，它们排序前后的相对前后顺序不会被打破。这在复杂对象排序中非常关键。

# 📉 为什么分治算法（以归并排序为例）的时间复杂度是 O(N log N)？

要搞懂为什么是 O(N log N)，我们需要把整个运行过程拆解成两部分来看：**树的高度（log N）** 乘以 **每一层的总工作量（N）**。

咱们用一棵“二叉树”的物理视角来把这个数学结论推导出来：

## 🏛️ 一、 物理视角：递归树的诞生

假设我们有一个长度为 $N$ 的数组（比如 $N = 8$）：

1. **第一层（顶部）**：整个大数组长度是 $N$。
2. **第二层（往下分一刀）**：切成两半，每半长度是 $N / 2$（即 4 和 4）。
3. **第三层（再往下分一刀）**：每半再切两半，长度变成 $N / 4$（即 2、2、2、2）。
4. **第 $k$ 层（触底）**：一直切到每个子数组长度只剩 **1**。

### ❓ 关键问题：这棵二叉树总共有多高？
- 每次把数组长度对半切（(N -> N/2 -> N/4 -> ... -> 1)）。
- 这本质上是一个数学问题：**数字 $N$ 连续除以多少次 2，结果才等于 1？**
- 答案是 **$\log_2 N$ 次**。
- **结论**：这棵递归树的**总高度（层数）就是 $\log N$**。

## ⚡ 二、 计算每一层的工作量

在归并排序中：
- **“分（Divide）”** 只是概念上的切分（通过切片索引指针），不产生实际的数据搬运开销，时间复杂度是 $\mathcal{O}(1)$。
- **真正的开销全在“治（Merge / 合并）”阶段**。

让我们看看每一层在合并时，总共需要做多少次比较和搬运：
- **最底层**：有 $N$ 个单独的元素，两两合并，总共要比较/搬运 $N$ 次。
- **中间某一层**：有若干个小数组在合并，但把这一层所有数组的长度加起来，**总元素个数依然刚好是 $N$**。
- **结论**：**无论在哪一层，把该层所有子数组合并起来的总工作量，永远都是线性 $\mathcal{O}(N)$。**

## 🚀 三、 终极相乘：O(N log N) 是怎么来的？

现在我们把这两部分拼起来：
- **总工作量 = 树的总层数 $\times$ 每一层的总工作量**
- **总工作量** = $\log N$（层数） $\times$ $N$（每层工作量） = **$\mathcal{O}(N \log N)$**。

这就是为什么只要符合“对半拆分（$\log N$ 层） + 每层全量合并（$\mathcal{O}(N)$）”特征的分治算法，时间复杂度铁定就是 $\mathcal{O}(N \log N)$！

# 🔍 为什么归并排序中“每一层的总工作量永远是 O(N)”？

这是学习分治算法时最精妙、也最容易让人卡壳的一个灵魂拷问。

为了让你彻底看清本质，我们抛开抽象的数学公式，直接拿**物理实物（切蛋糕和拼蛋糕）**来做个直观的类比。

## 🍰 一、 物理直觉：蛋糕碎了再拼，总质量变了吗？

假设手里有一块总长度为 $N = 8$ 的完整大蛋糕（比如长度代表 8 个数字）：

1. **第一层（最顶上）**：
   - 只有一个大整块，长度是 **8**。
   - 把它合并（其实还没开始切，就是它自己），我们需要处理的元素总数就是 **8**。

2. **第二层（切一刀后）**：
   - 大蛋糕被劈成两半，变成了两个小蛋糕，长度分别都是 **4**。
   - 现在我们要把这两半“治（Merge）”合起来。
   - 双指针在左边 4 个数和右边 4 个数之间来回比对、搬运。
   - **这一层总共处理了多少个元素？** 
     $$\text{左边 4 个} + \text{右边 4 个} = \mathbf{8 \text{ 个}}$$

3. **第三层（切两刀后）**：
   - 蛋糕碎成了 4 个小块，长度分别都是 **2**。
   - 现在我们要把这 4 个小块**两两合并**，变成 2 个中块。
   - **这一层总共处理了多少个元素？**
     $$\text{第 1 组}(2) + \text{第 2 组}(2) + \text{第 3 组}(2) + \text{第 4 组}(2) = \mathbf{8 \text{ 个}}$$

4. **最底层（切成渣渣）**：
   - 蛋糕被切成了 8 个单块，每个长度是 **1**。
   - 两两合并成 4 个小块。
   - **这一层总共处理了多少个元素？**
     $$1 + 1 + 1 + 1 + 1 + 1 + 1 + 1 = \mathbf{8 \text{ 个}}$$

## ⚖️ 二、 核心规律总结

你发现了吗？
无论是在第 1 层、第 2 层、第 3 层还是最底层：
- 虽然**碎片的块数**在成倍增加（1块 $\rightarrow$ 2块 $\rightarrow$ 4块 $\rightarrow$ 8块）。
- 每一块的**长度**在成倍减小（8 $\rightarrow$ 4 $\rightarrow$ 2 $\rightarrow$ 1）。
- **但是！把它们全部加起来的“总元素个数”，永远等于最初的总长度 N！**

这就好比你把一根 8 米长的铁丝剪成无数小段，不管你怎么剪、怎么在每一层把相邻的小段焊接（Merge）起来，**在同一层里所有正在被加工的铁丝总长度加起来，永远是 8 米，一毫米不多，一毫米不少。**

## ⚡ 三、 落实到双指针合并的代码上

在代码的 `merge` 函数中：
- 双指针扫过两个子数组时，每一个元素都**必须且只能被访问并搬运一次**。
- 如果这一层所有子数组的元素加起来正好是 $N$ 个，那么双指针在这一层把它们全部“拉链式”合流一遍，总共发生的操作次数就必然是 **$N$ 次**。

因此：
**无论在哪一层，所有子数组的长度总和恒等于 $N$，所以每一层的总工作量铁定就是线性的 $\mathcal{O}(N)$！**

```text
[ 3, 1 ]    [ 4, 1 ]    [ 5, 9 ]    [ 2, 6 ]  -----> 第 2 层 (总长度 2+2+2+2 = 8，合并工作量 = 8)
  /    \      /    \      /    \      /    \
[3]    [1]  [4]    [1]  [5]    [9]  [2]    [6]  ----> 第 3 层 (总长度 1×8 = 8，触底，递归出口)
```

### 🔍 结合这棵树，再来复盘那两个核心结论：

1. **为什么树的高度（层数）是 log N？**
   - 顶层的长度是 `8`。
   - 每往下走一层，长度就除以 2（`8 -> 4 -> 2 -> 1`）。
   - 从 8 变成 1，总共切了 3 次（因为 $2^3 = 8$，或者说 $\log_2 8 = 3$）。
   - 如果数组长度是 $N$，切到只剩 1 就要切 $\log N$ 层。这就是树的高度的由来。

2. **为什么每一层的总工作量永远是 N？**
   - **第 3 层（底）**：有 8 个长度为 1 的单元素。要把它们两两合并，总共要拉链式比对 8 次 $\rightarrow$ 总工作量 = 8。
   - **第 2 层**：有 4 个长度为 2 的小数组。要把它们两两合并成长度为 4 的数组，总共要拉链式比对 8 次 $\rightarrow$ 总工作量 = 8。
   - **第 1 层**：有 2 个长度为 4 的子数组。要把它们合并成长度为 8 的大数组，总共要拉链式比对 8 次 $\rightarrow$ 总工作量 = 8。
   - **结论**：每一层横向看过去，所有子数组加起来的元素总数永远是 $N$，所以每一层合并花掉的时间代价永远是 $\mathcal{O}(N)$。

### 🚀 最终汇聚
$$\text{总时间} = \text{树的总层数 } (\log N) \times \text{ 每层的总工作量 } (N) = \mathcal{O}(N \log N)$$

有了这棵树的物理空间感，以后不管谁问你归并排序为什么是 $\mathcal{O}(N \log N)$，你脑子里直接就能浮现出这个“横向切分、纵向合流”的经典金字塔结构了！🔥

# ⚖️ 排序算法没有绝对的“最好”，只有分情况讨论的“最契合”

在计算机科学中，著名的**“无免费午餐定理（No Free Lunch Theorem）”**告诉我们：**没有任何一个算法能在所有场景下都是最完美的。** 每一个排序算法都有它的“性格特征”和专属主场。

## 🛡️ 主流排序算法的 5 大核心战场与场景选择

| 战场（场景） | 代表算法 | 最好时间 | 平均时间 | 最坏时间 | 空间复杂度 | 稳定性 | 为什么选它 / 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **1. 通用安全场景** <br> (最怕最坏情况翻车) | **归并排序** <br> (Merge Sort) | O(N log N) | O(N log N) | **O(N log N)** | O(N) | 稳定 | **优点**：最坏情况稳如老狗，绝不退化。<br>**代价**：需要 O(N) 的额外内存。 |
| **2. 平均速度与内存平衡** | **快速排序** <br> (Quick Sort) | O(N log N) | O(N log N) | **O(N²)** | O(log N) | 不稳定 | **优点**：绝大多数随机数据下常数小、速度极快。<br>**缺点**：需防范极端恶心用例导致退化。 |
| **3. 内存极度紧张场景** <br> (嵌入式底层) | **堆排序** <br> (Heap Sort) | O(N log N) | O(N log N) | **O(N log N)** | **O(1)** | 不稳定 | **优点**：纯正的原地排序，空间开销极小。<br>**缺点**：对 CPU 缓存不友好，实际运行较慢。 |
| **4. 微型或基本有序场景** | **插入排序** <br> (Insertion Sort) | O(N) | O(N²) | **O(N²)** | O(1) | 稳定 | **优点**：在 N 很小或基本有序时，速度甚至快过快排与归并。 |
| **5. 极窄数值范围场景** | **计数排序 / 桶排序** | O(N + K) | O(N + K) | **O(N + K)** | O(K) | 稳定 | **优点**：打破比较排序极限，实现震撼的线性时间 O(N + K)。 |

## 💡 终极结论
- 如果面试考通用性、稳健性 $\rightarrow$ 首选**归并排序**。
- 如果追求极致的平均性能与空间优势（现代工业级标准库常采用混合排序，如内省排序/Timsort） $\rightarrow$ 结合**快排、归并与插入排序**的优势。
- 所以，没有绝对的“最好”，只有**“最契合当前业务场景和数据特征”**的算法选择！

### 75. Sort Colors
**Medium** | Topics | Companies | Hint

You are given an array `nums` with `n` objects colored red, white, or blue, sort them **in-place** so that objects of the same color are adjacent, with the colors in the order red, white, and blue.

We will use the integers `0`, `1`, and `2` to represent the color red, white, and blue, respectively.

You must solve this problem without using the library's sort function.

#### Example 1:
* **Input:** `nums = [2,0,2,1,1,0]`
* **Output:** `[0,0,1,1,2,2]`
* **Explanation:** The array has two 0s, two 1s, and two 2s. Sorting them in-place places all 0s first, then all 1s, then all 2s.

#### Example 2:
* **Input:** `nums = [2,0,1]`
* **Output:** `[0,1,2]`
* **Explanation:** The array has one each of 0, 1, and 2, arranged in-place in the order 0, 1, 2.

#### Constraints:
* `n == nums.length`
* `1 <= n <= 300`
* `nums[i]` is either `0`, `1`, or `2`.

#### Follow up:
Could you come up with a one-pass algorithm using only constant extra space?

### 为什么不用分治算法而用三指针？

从结果来看，用分治算法（比如刚才的归并排序）确实完全可以解出 **Sort Colors (LeetCode 75)**！因为它的最终目的确实也是把数组排好序。

不过，这道题有一个非常特殊的背景条件：**数组里只有 0、1、2 三种数字**。

#### 1. 如果用分治算法（归并排序）：
* **时间复杂度**：$O(n \log n)$
* **空间复杂度**：$O(n)$（需要切片或额外的辅助空间）

#### 2. 如果用三指针（荷兰国旗问题）：
这是官方更推荐、也更优雅的解法：
* **时间复杂度**：只需 **$O(n)$**（只需要对数组进行单趟遍历）
* **空间复杂度**：**$O(1)$**（直接在原地修改，不需要额外的辅助空间）

“荷兰国旗问题”三指针解法是解决这道题最经典、最优美的方案。它只需要单趟扫描（$O(n)$ 时间）并且原地修改（$O(1)$ 空间）。

### 核心思路

我们用三个指针把数组划分成四个区域：
* **`left`**：左边界指针。`left` 及其左边的元素全都是 `0`。
* **`right`**：右边界指针。`right` 及其右边的元素全都是 `2`。
* **`curr`**：当前遍历指针。负责扫描整个数组。

在扫描过程中，我们让 `curr` 从左向右移动：
* 如果 `nums[curr] == 0`：把它换到左边去。`nums[curr]` 和 `nums[left]` 交换，然后 `left` 和 `curr` 同时向右移动。
* 如果 `nums[curr] == 2`：把它换到右边去。`nums[curr]` 和 `nums[right]` 交换，然后只有 `right` 向左移动（注意：此时 `curr` 不能动，因为从右边换过来的那个未知元素还需要重新检查一遍）。
* 如果 `nums[curr] == 1`：它本来就该在中间，`curr` 直接向右移动。

### Python 代码实现

```python
class Solution:
    def sortColors(self, nums: list[int]) -> None:
        """
        Do not return anything, modify nums in-place instead.
        """
        left = 0
        curr = 0
        right = len(nums) - 1

        while curr <= right:
            if nums[curr] == 0:
                # 把 0 换到左边
                nums[left], nums[curr] = nums[curr], nums[left]
                left += 1
                curr += 1
            elif nums[curr] == 2:
                # 把 2 换到右边
                nums[curr], nums[right] = nums[right], nums[curr]
                right -= 1
                # 注意：这里 curr 不能加 1，因为换过来的新元素还没检查过
            else:
                # 是 1 的话直接跳过
                curr += 1
```

### 复杂度

* **时间复杂度**：$O(n)$，只需要对数组遍历一次。
* **空间复杂度**：$O(1)$，纯原地交换，没有使用任何额外的空间。

在 Python（以及大多数支持原地修改对象的编程语言）中，**数组是通过引用传递的**。

### 核心原因

方法签名是：
```python
def sortColors(self, nums: list[int]) -> None:
```

注意它的返回类型标注是 `-> None`。也就是说，LeetCode 的测试框架调用这个函数时，并不期望你返回任何东西。

它只关心你是否直接修改了原数组（`in-place`）：
* 你传进来的 `nums` 指向内存中的同一个列表对象。
* 你在函数里通过交换元素（`nums[left], nums[curr] = nums[curr], nums[left]`）直接把这块内存里的数据排好了序。
* 当函数执行结束后，LeetCode 的测试程序会自动去检查你传进去那个 `nums` 变量，看看它现在变成什么样了。

所以，你**不需要、也不应该写 `return nums`**（虽然写了也不会报错，但类型标注是 `None`，写了也没有实际意义）。
